# Per-test fake clients stay; no shared `FakeClient`

The snapshot tests define ~8 client doubles named `_FakeClient` (plus `_FailingClient`, `_CountingClient`, `_Client404`, etc.) across `tests/audit/test_snapshot.py`, `test_snapshot_agents.py`, `test_snapshot_targets.py`, and `user_permission/test_user_snapshot.py`. An architecture review flagged this as duplication to collapse onto one shared `FakeClient`. We **decline**: the doubles share a *name* and the `get`/`paginate` *shape*, but not an interface (the facts a caller must know -- how you configure it, what it routes on, what it raises). Consolidating them would lower locality and add coupling for no real shared behaviour.

## Considered Options

1. **One shared `FakeClient` for all snapshot tests.** Rejected. The doubles satisfy three genuinely different micro-contracts: `test_snapshot.py` is a `set_get`/`set_paginate` *recorder* that raises on unexpected paths; `test_snapshot_agents.py` has four tiny *single-behaviour* doubles (return-fixed-count, raise-404, count-head-requests, propagate-timeout), each 5 lines, returning exactly the one response its test asserts on; `test_snapshot_targets.py` is a *constructor-configured path-router* (`__init__(sites, targets_by_site)`, parses the site id out of the URL). A fake general enough to express all three would force every test to configure a heavier shared surface to reproduce its bespoke stimulus -- the test's intent would then live half in the test and half in the shared fake. That is the shallow-extraction anti-pattern, not a deepening.

2. **Consolidate only the recorder family across files.** Rejected as not worth it. `test_snapshot.py` and `user_permission/test_user_snapshot.py` each have a recorder-style base `_FakeClient`, but they record *different* endpoint surfaces (`EnvSnapshot`'s sites/credentials/templates vs `UserSnapshot`'s users/2FA/auth-sources) and each already shares its own fake within its file via error-injecting subclasses (`_Client404`, `_Client500`, `_ClientGateway`, `_Client2FA`). They reuse the *name* `_FakeClient` for two different snapshots' contracts; a cross-file base would couple the two test modules to one fake whose surface is the union of both.

## Consequences

- The fakes are already consolidated at the right granularity: **per file, by inheritance where it pays** (the `_Client404`/`_Client500`/`_ClientGateway` subclasses of a file's base recorder) and **inline where the double is trivial** (the agents single-behaviour doubles). The duplication the review saw is the reused *name*, not duplicated behaviour.
- Applying the deletion test: deleting a hypothetical shared `FakeClient` would **not** concentrate complexity, because the complexity (each test's specific stimulus/response) is inherent to each test and does not live in a shared place today. "One adapter is a hypothetical seam, two is a real one" -- here there are many doubles but they do not sit at one seam; they satisfy many micro-contracts.
- This is the explicit "no" so a future architecture review does not re-suggest the shared fake on seeing ~8 `_FakeClient` definitions. If a real shared interface ever emerges (e.g. several tests independently grow the *same* `set_get`/`set_paginate` recorder for the *same* snapshot), revisit then -- two genuine adapters at one seam would justify it.
