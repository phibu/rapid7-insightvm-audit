# 0.2.13 -- Engine OS gap doc + scan_*.py style cleanups

**Status:** design
**Date:** 2026-05-06
**Target version:** 0.2.13 (patch)
**Source backlog items:**
- `0.2.4 / feature` -- engine OS support rule (resolved as v3 API gap, doc only)
- `someday / cleanup` -- `scan_engines.py` parallel status dicts
- `someday / cleanup` -- `scan_activity.py` recent-status block duplication

## Summary

Three independent, low-risk changes shipped together as 0.2.13:

1. Document the lack of engine-host OS data in the v3 API as a known gap in the README's existing "Rules NOT implemented" section.
2. Consolidate the parallel `_BAD_STATUS_SEVERITY` and `_BAD_STATUS_REASON` dicts in `checks/scan_engines.py` into a single `NamedTuple`-valued mapping.
3. Extract a `_recent_status_rule(...)` helper in `checks/scan_activity.py` to deduplicate the structurally identical `recent_failed_scans` and `recent_unknown_scans` blocks.

No new functionality. No HTTP changes. No config schema changes. No new rule_ids. All existing rule_ids preserved verbatim for delta-blob continuity.

## Motivation

The 0.2.4 backlog asked for two engine-related rules: version drift (already shipped under `engine_version_drift.py`) and OS-support currency. The v3 OpenAPI `ScanEngine` schema (`docs/research/api-v3.json`) exposes only `id`, `name`, `address`, `port`, `status`, `productVersion`, `contentVersion`, `lastRefreshedDate`, `lastUpdatedDate`, `sites`, and `enginePools`. There is no engine-host OS field. Per the established CLAUDE.md pattern ("If a feature genuinely cannot be implemented read-only [or because the data doesn't exist], document it as a v3 API gap"), this becomes a doc entry rather than a new rule.

The `someday`-tagged cleanups are mechanical drift-prevention work in two op-checks that have grown small structural duplications. Bundling them with the doc change avoids a release ceremony per item.

## Read-only safety

None of these changes issue HTTP. `client.py` is untouched. The verb allowlist (`GET` only, plus the single allowlisted POST to `/api/3/assets/search`) is unchanged. The doc change is plain text. The two cleanups are pure-Python refactors of existing in-process logic. CLAUDE.md "Read-only safety" requirements are satisfied trivially.

## Component 2 -- `scan_engines.py` status table consolidation

### Where

`src/rapid7_healthcheck/checks/scan_engines.py`. The two module-level constants `_BAD_STATUS_SEVERITY` and `_BAD_STATUS_REASON`, plus their lookup sites inside the bad-status branch.

### Today's shape

Two parallel dicts keyed on the same v3 `ScanEngine.status` enum string. Adding a status to one and forgetting the other is a real drift risk; the existing comment in the backlog flags this explicitly.

### Target shape

Replace both dicts with a single mapping whose values carry both severity and reason. Use `typing.NamedTuple` for clarity (matches the project's preference for stdlib over third-party). Approximately:

```python
from typing import Literal, NamedTuple

class _BadStatus(NamedTuple):
    severity: Literal["info", "warn", "fail"]
    reason: str

_BAD_STATUS: dict[str, _BadStatus] = {
    "unreachable":  _BadStatus("fail", "<existing reason text>"),
    # ...one entry per current key in either dict
}
```

Lookup sites change from `_BAD_STATUS_SEVERITY[status]` / `_BAD_STATUS_REASON[status]` to `_BAD_STATUS[status].severity` / `_BAD_STATUS[status].reason`.

### Invariants

- Every status currently keyed in either old dict appears in `_BAD_STATUS` with the same severity and the same reason text.
- Severity values come from the existing dict verbatim; do not re-classify.
- Reason text comes from the existing dict verbatim.
- The bad-status branch's behaviour for unknown/missing statuses is preserved (see implementation plan for handling).
- All existing tests in `tests/checks/test_scan_engines*.py` pass unchanged.

### Out of scope

- No change to which statuses are flagged.
- No change to severity per status.
- No change to message text.
- No new statuses.

## Component 3 -- `scan_activity.py` `_recent_status_rule` helper

### Where

`src/rapid7_healthcheck/checks/scan_activity.py`. The two methods (or method-bodies) that produce the `op.scan_activity.recent_failed_scans` and `op.scan_activity.recent_unknown_scans` rule results.

### Today's shape

Two blocks that are structurally identical: counter pair (per-site / total), per-finding emit with a cap, overflow rollup finding, and a `make_rule_result(...)` call. They differ only in:

- the `target_status` string compared against scan status (`"failed"` vs an unknown-state predicate).
- the `rule_id`, `rule_name`, `description`, `sources` strings.
- the threshold-config key consulted.

### Target shape

A private helper at module scope:

```python
def _recent_status_rule(
    *,
    rule_id: str,
    rule_name: str,
    description: str,
    sources: list[str],
    severity: Severity,
    status_predicate: Callable[[str], bool],
    scans_iter: Iterable[dict],
    cap: int,
    threshold_days: int,
    site_name_lookup: Callable[[int | str], str | None],
) -> RuleResult:
    ...
```

(Final signature determined during implementation; this is the contract -- same inputs both call sites today need, same output shape.)

`status_predicate` rather than `target_status: str` so the unknown-state rule (which matches anything outside the v3 `ScanStatus` enum, see commit `de25edb`) keeps its existing semantics. The failed-scans branch passes a predicate that matches exactly `"failed"`.

Both call sites become single `_recent_status_rule(...)` invocations. The two existing `rule_id`s -- `op.scan_activity.recent_failed_scans` and `op.scan_activity.recent_unknown_scans` -- are preserved verbatim. **This is non-negotiable**: report state-blob signatures key on rule_id and changing them would silently break delta-blob continuity for users carrying a 0.2.12 prior-state file forward.

### Invariants

- Both rule results have identical `rule_id`, `rule_name`, `description`, `sources`, severity, finding count, message text, and `summary` shape compared to 0.2.12.
- Cap and rollup behaviour identical.
- Site-name lookup behaviour identical (whatever fallback is used today: name-or-id-string).
- All existing tests in `tests/checks/test_scan_activity*.py` pass unchanged.

### Out of scope

- No change to thresholds.
- No change to status-classification logic.
- No new rule_ids.
- No restructuring of the other rule-bearing methods in this check (those belong to the 0.3.0 per-rule isolation refactor).

## Risks

- **Delta-blob continuity.** Any rename of a `rule_id` on the cleanup path silently breaks state-blob continuity for users upgrading from 0.2.12. Mitigation: the spec calls out preservation of `op.scan_activity.recent_failed_scans` / `recent_unknown_scans`; the implementation plan must include a verification step that diffs the rule_id set before/after.
- **Behaviour drift on `_BAD_STATUS`.** Copy-pasting reason text from one dict to another invites typos. Mitigation: the implementation plan must include a test-driven verification step that the new `_BAD_STATUS` mapping yields the same reason for every status the old dicts named.
- **Scope creep.** "While I'm here" temptations on `scan_engines.py` / `scan_activity.py` belong to 0.3.0 (per-rule isolation), not here. Mitigation: the implementation plan keeps the diff narrow and rejects unrelated changes.
