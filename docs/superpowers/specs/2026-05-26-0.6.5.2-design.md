## Bug-by-bug design

### B3 — `duration_ms` zero on op-check rule cards

**Root cause (different from backlog item).** The backlog item proposed wrapping every `make_rule_result(...)` call with `time.monotonic()` and threading `duration_ms` through. Reading `_op_rule.py:122-156` shows a simpler fix:

- `safe_run_rule()` → `safe_run()` already records `rule_start = time.monotonic()` and on the **error path** computes `duration_ms = int((time.monotonic() - rule_start) * 1000)`.
- On the **success path** it does `return fn()` directly. `fn()` is the rule's `make_rule_result(...)` call, which defaults `duration_ms` to 0.

So the fix lives in `safe_run`: after `result = fn()`, return a copy of the result with `duration_ms` set to the measured value. Single edit point covers all 4 op-checks (scan_engines, scan_activity, asset_coverage, data_quality) and every rule under them. No change to `make_rule_result`, no per-call-site sweep.

**Implementation:**
```python
def safe_run(fn, *, rule_id, rule_name, description, sources=(), default_severity="warn"):
    rule_start = time.monotonic()
    try:
        result = fn()
    except Exception as e:
        # ... existing error_rule path, unchanged ...
    duration_ms = int((time.monotonic() - rule_start) * 1000)
    # Don't clobber a non-zero duration_ms the rule explicitly set (currently
    # none do, but the rule contract allows it).
    if result.duration_ms == 0:
        return replace(result, duration_ms=duration_ms)
    return result
```

`replace` is `dataclasses.replace`. `RuleResult` is already a dataclass, so this works without changes there.

**Why preserve a pre-set non-zero `duration_ms`:** keeps the door open for rules that want to report their own timing (e.g. external-call subtotal). No current rule does this, but breaking the override would be a silent semantic change.

**Verification:** existing rule tests that build `RuleResult` directly continue to assert `duration_ms == 0`. New test asserts that going through `safe_run`/`safe_run_rule` produces `duration_ms > 0` for a rule that does measurable work (e.g. small `time.sleep`).

**Sanity check:** confirm `asset_coverage.py` and `data_quality.py` also route through `safe_run_rule`. If any op-check builds `make_rule_result` outside `safe_run_rule`, that one path needs a separate fix.

### B2 — Local engine wrongly flagged for missing `lastRefreshedDate`

**Root cause:** `checks/scan_engines.py:149-181` (`EngineMissingLastRefreshRule`) iterates every engine and flags any with no `lastRefreshedDate`. The local scan engine (in-process, default name `"Local scan engine"`) never has one by design — it's not a refreshed peer.

**Fix:** import `_is_local_engine` and `_DEFAULT_LOCAL_NAMES` from `audit/rules/local_engine_production_scope.py`, exclude local engines in this rule's loop. Also honor the same `additional_local_names` knob via this rule's `rule_config` if accessible — **but** op-check rules don't currently receive `rule_config`. Two options:
- (a) Only use the default `_DEFAULT_LOCAL_NAMES` set. Operators who renamed their local engine miss the exclusion. Pragmatic, ships in one file.
- (b) Plumb `rule_config` to op-checks. Out of scope for a patch release.

**Decision:** (a). Document the limitation in the rule's docstring. If a real user with a renamed local engine reports it, escalate to a 0.6.6 fix that adds the knob.

**Cross-module import concern:** `checks/scan_engines.py` importing from `audit/rules/local_engine_production_scope.py` reverses the natural dependency (checks shouldn't depend on audit rules). The cleanest move is to extract `_is_local_engine` + `_DEFAULT_LOCAL_NAMES` into a shared helper module, e.g. `checks/_local_engine.py` or `audit/_local_engine.py`. Both files import from it.

**Decision:** extract to `src/rapid7_healthcheck/_local_engine.py` (top-level, since both verticals consume it). Move the predicate + constants there; update both call sites. Keeps the dependency clean.

**Verification:** test that an engine named `"Local scan engine"` with `lastRefreshedDate: None` produces zero findings; a different engine named `"engine-01"` with missing `lastRefreshedDate` still does. Test the loopback-address branch too.

### B1 — `EngineUnpairedRule` ignores engine pools

**Root cause:** `checks/scan_engines.py:184-231` reads `engine.get("sites")`. Per the v3 spec (`docs/research/api-v3.json`), `ScanEngine.sites` only carries **direct** site assignments. Pool-mediated assignments live on `EnginePool.engines[]` + `EnginePool.sites[]`. An engine that's bound to sites only through a pool reports `sites: []` and gets falsely flagged as unpaired.

**Verified endpoints (read-only, GET):**
- `GET /api/3/scan_engine_pools` — collection of all pools, each with `engines[]` (engine IDs) and `sites[]` (site IDs)
- `GET /api/3/scan_engines/{id}/scan_engine_pools` exists too but iterating it is N+1; bulk listing wins

**Snapshot accessor (new):** add `scan_engine_pools()` to `EnvSnapshot`. Single GET, returns `list[dict]` from `body.get("resources", [])` — mirroring `scan_engines()`. The endpoint takes no `page`/`size` per v3 spec (verify against `api-v3.json`). Cache like every other accessor.

**Rule change:** `ScanEnginesCheck.run` builds a `pooled_sites_by_engine: dict[int, set[int]]` index from the new accessor (engine_id → set of site_ids reachable via any pool the engine belongs to). Pass that index into `EngineUnpairedRule.run()` as a second arg. Inside the rule:

```python
direct_sites = engine.get("sites") or []
pooled_sites = pooled_sites_by_engine.get(engine.get("id"), set())
if direct_sites or pooled_sites:
    continue
```

`details` dict gets a new key `pool_sites_count` for diagnostic context (always 0 in flagged findings; useful in the "wait, why wasn't this engine flagged?" debugging story).

**Failure mode:** if `/api/3/scan_engine_pools` returns 404 (very unlikely — endpoint is in every published v3 spec, but defensive) or any error, treat as "no pool data available" — pool-mediated engines fall back to the old (buggy) behavior. The accessor catches `Rapid7ClientError(status_code=404)` and returns `[]`, logging a warning. Other errors propagate (the rule wraps in `safe_run_rule`, so they surface as an error rule card).

**Verification (TDD):**
- New test: engine with `sites: []` whose `id` is in a pool's `engines: [...]` AND that pool has `sites: [non-empty]` → NOT flagged.
- New test: engine with `sites: []` not in any pool → still flagged (regression guard).
- New test: engine with `sites: [direct-site]` AND also in a pool → still not flagged (was already correct, but confirm).
- New test: snapshot accessor returns `[]` on 404, logs warning.

### B4 — Dead `id=N` fallback in `single_engine_overload`

**Root cause analysis:** `audit/rules/single_engine_overload.py:43` reads `engines_by_id.get(engine_id, {}).get("name", f"id={engine_id}")`. `engines_by_id` is built from `snapshot.scan_engines()` (all engines on the console). `sites_by_engine` is keyed off `site["scanEngine"]` — which is a **direct** assignment only. So every engine in `sites_by_engine` is direct-assigned and MUST exist in `scan_engines()`. The fallback can only fire if a site references a scan engine that doesn't exist in the console listing — a pathological inconsistency, not a real case.

**Post-B1 status:** B1 only adds pool-aware logic to `EngineUnpairedRule`. `single_engine_overload.py` is **separate** — it already only counts direct assignments via `site["scanEngine"]`. B1 doesn't add pool-assigned engines to `sites_by_engine` in this rule. So:
- Before B1: fallback is dead unless data is corrupt.
- After B1: same.

**Decision:** leave the fallback as a defensive safety net. Document it in a one-line comment so the next reader doesn't flag it again. **No code change in B4** — close the backlog item as "verified, kept as defensive guard." This matches the user's "leave it as a safety net but verify it can never fire" option.

**Important caveat for 0.6.6 follow-up:** if 0.6.6 expands `single_engine_overload` to include pool-assigned engines (legitimate: pool fan-out is real load), then a pool-only engine entering `sites_by_engine` could theoretically not be in `scan_engines()` if a pool references a stale engine ID — and the fallback would then matter. Backlog for 0.6.6 to consider.

## Risk assessment

- **B3** is the most invasive (affects every op-check), but the change is one method in `_op_rule.py`. Risk is low because existing tests still pass — they assert findings/status, not duration_ms.
- **B2** is small and isolated. The cross-module extraction is mechanical.
- **B1** is the biggest. Adding a new snapshot accessor and changing a rule's signature. Mitigated by (a) the snapshot accessor mirrors existing patterns exactly, (b) the rule change is additive (OR with new data source), (c) 404-handling falls back to current behavior.
- **B4** is a no-op (just a comment).
