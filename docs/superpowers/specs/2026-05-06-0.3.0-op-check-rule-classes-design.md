# 0.3.0 -- Op-check rule isolation + class-shaped rules with identity constants

**Status:** design
**Date:** 2026-05-06
**Target version:** 0.3.0 (minor)
**Source backlog items (cleared on ship):**
- `0.3.0 / important` -- Extend per-rule isolation pattern to `scan_engines.py` and `scan_activity.py`.
- `0.3.0 / cleanup` -- Extract per-rule identity constants on each op-check rule.

## Summary

Two coupled refactors shipped in one release.

1. Extend the per-rule isolation pattern (`safe_run(lambda: ...)` plus per-rule error containment) from `asset_coverage.py` and `data_quality.py` to `scan_engines.py` and `scan_activity.py`. Both checks today compute multiple finding buckets in a single `run()`-body loop with no per-rule methods to wrap; that structure is replaced with one rule class per concept.
2. Convert every op-check rule across all four check files to a class-shaped rule with class-level identity constants (`RULE_ID`, `RULE_NAME`, `DESCRIPTION`, `DEFAULT_SEVERITY`, `SOURCES`). This is the "identity-constants extraction" cleanup the backlog calls for. It eliminates today's identity duplication between `safe_run` call sites and rule-method bodies. All four op-check files convert in the same release so the codebase ships uniform rather than half-converted.

**No behavior change.** Every existing op-check `rule_id` is preserved verbatim (delta-blob continuity is non-negotiable). Every existing rendered finding message is preserved byte-identical. Every existing `CheckResult.summary` field is preserved.

## Motivation

The backlog flags two related issues. First, `scan_engines.py` and `scan_activity.py` are the last two op-checks that haven't adopted the per-rule isolation pattern; one rule's exception today aborts the entire check, hiding the surviving rules' findings from the report. Second, every op-check rule duplicates its identity (`rule_id`, `rule_name`, `description`, `sources`) across the `safe_run` call site and the rule-method body. Today's drift-guard test catches `rule_id` drift but description/name drift would still slip through. The backlog notes that splitting these would leave the codebase asymmetric ("the asymmetry is worse than the duplication"), so they ship together.

## Read-only safety

This is pure-Python restructuring. No HTTP changes. `client.py` is untouched. The verb allowlist (`GET` only, plus the single allowlisted POST to `/api/3/assets/search`) is unchanged. The implementation plan will include a verification step (`git diff <baseline>..HEAD -- src/ | grep -nE 'PUT|PATCH|DELETE|client\.(put|patch|delete)'` returning zero matches) before tagging.

## Architecture

### Today's pattern (the two checks already isolated)

`asset_coverage.py` and `data_quality.py` use the pattern below:

```python
class AssetCoverageCheck:
    def run(self, client, config, *, snapshot=None) -> CheckResult:
        rule_results = [
            safe_run(
                lambda: self._stale_assets(client, t),
                rule_id="op.asset_coverage.stale_assets",
                rule_name="Stale assets",
                description="Assets whose last scan is older than ...",
                sources=[_SRC_FILTERED_SEARCH],
            ),
            ...
        ]

    def _stale_assets(self, client, t) -> RuleResult:
        rid = "op.asset_coverage.stale_assets"     # duplicated
        name = "Stale assets"                       # duplicated
        desc = "Assets whose last scan is older..." # duplicated
        sources = [_SRC_FILTERED_SEARCH]            # duplicated
        ...
```

Identity is duplicated between the call site (used by `safe_run` to synthesize an `error_rule` if the body raises) and the method body (used to construct the `make_rule_result(...)` on the success path). Drift is possible.

### Target pattern

Each rule becomes a self-contained class. Identity lives in class-level constants. Both call sites read from those constants.

```python
class StaleAssetsRule:
    RULE_ID = "op.asset_coverage.stale_assets"
    RULE_NAME = "Stale assets"
    DESCRIPTION = (
        "Assets whose last scan is older than the stale threshold "
        "(coverage gap, but not yet expired)."
    )
    DEFAULT_SEVERITY: Severity = "warn"
    SOURCES: tuple[str, ...] = (_SRC_FILTERED_SEARCH,)

    def run(self, client, t) -> RuleResult:
        ...
        return make_rule_result(
            rule_id=self.RULE_ID,
            rule_name=self.RULE_NAME,
            description=self.DESCRIPTION,
            findings=findings,
            sources=self.SOURCES,
            summary={...},
            default_severity=self.DEFAULT_SEVERITY,
        )


class AssetCoverageCheck:
    def run(self, client, config, *, snapshot=None) -> CheckResult:
        stale = StaleAssetsRule()
        rule_results = [
            safe_run_rule(stale, lambda: stale.run(client, t)),
            ...
        ]
```

A new helper `safe_run_rule(rule, fn)` in `_op_rule.py` collapses the call-site boilerplate by reading the five class attributes off `rule` and dispatching to the existing `safe_run`:

```python
def safe_run_rule(rule, fn: Callable[[], RuleResult]) -> RuleResult:
    return safe_run(
        fn,
        rule_id=rule.RULE_ID,
        rule_name=rule.RULE_NAME,
        description=rule.DESCRIPTION,
        sources=rule.SOURCES,
        default_severity=rule.DEFAULT_SEVERITY,
    )
```

`safe_run` keeps its existing signature unchanged. Callers can still use it directly if a one-off identity is needed (none today; all four checks migrate to `safe_run_rule`).

No registry, no `Protocol`, no decorator. Each check's `run()` enumerates its rules explicitly, the same way it does today. The class shape exists purely to put each rule's identity in one place.

## Components

### 1. `_op_rule.py` -- add `safe_run_rule`

New helper, ~12 lines. Reads the five class-level identity attributes off any object that has them and dispatches to existing `safe_run`. Existing helpers (`safe_run`, `make_rule_result`, `error_rule`, `skipped_rule`, `rollup_check_status`, `flatten_findings`, `rule_summary`) stay unchanged. No breaking changes; no removals.

### 2. `scan_engines.py` -- four new rule classes

Convert today's single-loop `run()` body into four rule classes, each producing its own `RuleResult`:

- **`EngineBadStatusRule`** -- `RULE_ID = "op.scan_engines.bad_status"`, `DEFAULT_SEVERITY = "fail"`. Iterates the engine list and surfaces engines whose `status` is keyed in the existing `_BAD_STATUS` mapping (the 0.2.13 NamedTuple-valued dict stays as-is).
- **`EngineLastContactRule`** -- `RULE_ID = "op.scan_engines.last_contact"`, `DEFAULT_SEVERITY = "warn"`. Surfaces engines whose `lastRefreshedDate` exceeds the warn or fail threshold.
- **`EngineMissingLastRefreshRule`** -- `RULE_ID = "op.scan_engines.missing_last_refresh"`, `DEFAULT_SEVERITY = "warn"`. Surfaces engines that report no `lastRefreshedDate`.
- **`EngineUnpairedRule`** -- `RULE_ID = "op.scan_engines.unpaired"`, `DEFAULT_SEVERITY = "warn"`. Surfaces engines configured on the console but not assigned to any site.

Each rule's `run(self, engines, t) -> RuleResult` takes the already-fetched engine list and the `thresholds.scan_engines` slice. The rules iterate the engine list independently (option A from brainstorm question 3) -- fleets are small, so re-iterating four times is cheap.

`ScanEnginesCheck.run()` becomes:
1. One `client.get("/api/3/scan_engines")` call to fetch the engine list.
2. Instantiate all four rule classes.
3. Build `rule_results = [safe_run_rule(r, lambda: r.run(engines, t)) for r in rules]`. (Spelled out per-rule for readability rather than a comprehension, to make the call sites explicit.)
4. Compute the cross-rule engine-count summary via a new helper `_compute_engine_count_summary(engines, rule_results)` that walks the rule_results' findings, deduplicates per-engine-id, and rolls up worst severity (option B from brainstorm question 4 -- preserves the current `engines_total`/`engines_healthy`/`engines_warn`/`engines_fail` summary keys).
5. Build the `CheckResult` with `rule_results`, `flatten_findings(rule_results)`, `rollup_check_status(rule_results)`, and the merged summary.

The existing `_BAD_STATUS` / `_BadStatus` (0.2.13) and `_parse_iso` helpers stay at module scope, used by the relevant rule classes.

### 3. `scan_activity.py` -- six new rule classes + a small parsed-data layer

The current `ScanActivityCheck.run()` does one pass over `client.paginate("/api/3/sites")` plus per-site `client.get(f"/api/3/sites/{site_id}/scans", ...)`, then a per-scan loop that fans out into six finding buckets. Splitting that into six rule methods naively would multiply API cost by 6× (each method re-paginating). To preserve API cost while isolating rules, `run()` does the I/O up front into a local intermediate, then each rule reads from that intermediate.

**Local intermediate types (file-scoped, not promoted to `EnvSnapshot`):**

```python
@dataclass(frozen=True)
class _ParsedScan:
    scan_id: int | None
    status: str
    start_time: datetime | None  # parsed once, here

@dataclass(frozen=True)
class _ParsedSiteScans:
    site_id: int | None
    site_name: str
    scans: tuple[_ParsedScan, ...]
    most_recent_finished: datetime | None
    has_any_scans: bool   # convenience: scans != ()
```

`ScanActivityCheck.run()` shape:
1. Iterate `client.paginate("/api/3/sites")`. For each site, fetch its recent scans (`/api/3/sites/{id}/scans`, sort=startTime DESC, size=20) and parse the response into one `_ParsedSiteScans` row. Append to a local `parsed_sites: list[_ParsedSiteScans]`.
2. Instantiate the six rule classes.
3. Build `rule_results` via six `safe_run_rule(...)` calls, each rule taking `parsed_sites` plus the relevant threshold-config slice.
4. Build the `CheckResult` with `rule_summary(rule_results)` (the existing tile-strip summary; `scan_activity` does not have a custom cross-rule summary like `scan_engines`).

**Six rule classes:**

- **`SitesNeverScannedRule`** -- `op.scan_activity.sites_never_scanned`, `DEFAULT_SEVERITY = "fail"`. Sites where `has_any_scans is False`.
- **`SitesNoSuccessfulScanRule`** -- `op.scan_activity.sites_no_successful_scan`, `DEFAULT_SEVERITY = "fail"`. Sites with scan history where `most_recent_finished is None`.
- **`StuckScansRule`** -- `op.scan_activity.stuck_scans`, `DEFAULT_SEVERITY = "fail"`. Scans whose status is `"running"` and whose `start_time` is older than the stuck-scan threshold.
- **`RecentFailedScansRule`** -- `op.scan_activity.recent_failed_scans`, `DEFAULT_SEVERITY = "warn"`. Subsumes the `_RECENT_STATUS_RULES[0]` row from 0.2.13 -- predicate `lambda s: s in _FAILED_STATUSES`, message phrase `"a {status} scan"`, overflow label `"failed scans"`.
- **`RecentUnknownScansRule`** -- `op.scan_activity.recent_unknown_scans`, `DEFAULT_SEVERITY = "warn"`. Subsumes `_RECENT_STATUS_RULES[1]`.
- **`SitesOverdueScansRule`** -- `op.scan_activity.sites_overdue_scans`, `DEFAULT_SEVERITY = "warn"`. Sites whose `most_recent_finished` is past the recent-window threshold (warn) or past the site-no-scan threshold (fail). Also produces the `sites_with_recent_scans` and `sites_total` summary fields (currently surfaced on the corresponding `make_rule_result(...)` call).

**0.2.13 helpers retained:**
- `_RECENT_STATUS_RULES` (tuple of `_RecentStatusRule`) and `_emit_overflow_rollup` are used by `RecentFailedScansRule` and `RecentUnknownScansRule` only. They can either stay at module scope (simplest) or migrate into the two rule classes. Implementation choice -- call out in the plan; recommendation is to keep them at module scope to minimize the diff and because they're shared by two rules.
- `_FAILED_STATUSES` and `_MAX_FAILED_FINDINGS` stay at module scope.
- `_parse_iso` stays at module scope.

### 4. `asset_coverage.py` -- convert four existing methods to rule classes

Today's `AssetCoverageCheck` has four `safe_run(lambda: self._method(...), rule_id=..., ...)` call sites and four `_method` bodies that re-declare identity strings. Each method becomes a class:

- `_stale_assets` → `StaleAssetsRule` (`op.asset_coverage.stale_assets`).
- `_never_scanned_assets` → `NeverScannedAssetsRule` (`op.asset_coverage.never_scanned_assets`).
- `_dead_asset_groups` → `DeadAssetGroupsRule` (`op.asset_coverage.dead_asset_groups`).
- `_agent_only_assets` → `AgentOnlyAssetsRule` (`op.asset_coverage.agent_only_assets`).

Each new class takes whatever the existing method's signature took (`client`, `t`, sometimes `snapshot`, sometimes `config.audit`). The body is unchanged except that the identity-string declarations at the top of the method are deleted (constants live on the class) and the `make_rule_result(...)` call now reads `self.RULE_ID` / `self.RULE_NAME` / `self.DESCRIPTION` / `self.SOURCES` / `self.DEFAULT_SEVERITY`.

Module-level helpers (`_per_asset_findings`, `_capped_findings_with_rollup`, `_example_hostnames`, `_asset_label`, etc.) stay where they are, used by the rule classes. `AssetCoverageCheck.run()` simplifies to instantiate-and-dispatch via `safe_run_rule`.

### 5. `data_quality.py` -- same conversion

`data_quality.py` has rule methods today (the implementation plan will enumerate them by reading the file; the spec doesn't pre-bind to specific method names because the plan is the place for verbatim file content). Each becomes a class with class-level identity constants. `DataQualityCheck.run()` simplifies the same way.

### 6. Tests -- migrate `tests/checks/test_scan_*.py`

The backlog explicitly calls out test migration: "migrate every test in `tests/checks/test_scan_*.py` from flat-finding-list assertions to per-rule-result assertions."

**Migration pattern:**
- Existing assertions on `result.findings[i]` (the flat list) become assertions on `result.rule_results[i].findings` looked up by `rule_id` via the existing `_rule(result, rule_id)` test helper (already used in `tests/checks/test_scan_activity.py` for the recent-failed and recent-unknown rules added in 0.2.13's predecessor work).
- Tests that currently assert `result.summary["engines_healthy"]` etc. continue to work unchanged (the public summary keys are preserved by the new `_compute_engine_count_summary` helper).
- Tests that asserted on the flat `result.findings` length now assert on `_rule(result, "...").findings` lengths or on `rule_results` count.
- The drift-guard test that today asserts every method's `rid` matches the call-site `rule_id` becomes a test that asserts every rule class's `RULE_ID` matches what the check's `run()` instantiates.

**`tests/checks/test_asset_coverage.py` and `tests/checks/test_data_quality.py`:** these are mostly already in the per-rule-result shape (they were written when those checks adopted isolation), but every assertion that referenced an old method-style identity (e.g. accessing `AssetCoverageCheck()._stale_assets` directly) must update to instantiate the new rule class and call its `run(...)` method. The plan-time read of these files will surface the exact locations.

### 7. Drift-guard test

Today's drift-guard test (location TBD by plan-time read; it's the test the backlog mentions catching `rule_id` drift between call site and method body) becomes redundant -- class-level constants are read by both call sites, so they cannot drift. Replace with a test that asserts every check's `run()` method constructs every rule class declared in its module, indirectly verifying that no rule was orphaned during the migration.

## Invariants (load-bearing -- non-negotiable)

1. **Every existing rule_id is preserved verbatim.** Enumeration before/after must match exactly. The implementation plan includes a `git grep` verification step.
2. **Every rendered finding message is byte-identical to 0.2.13.** Existing tests gate this; if any test's message-string assertion breaks, the migration is wrong.
3. **Every `CheckResult.summary` field is preserved.** Specifically `scan_engines`'s `engines_total`/`engines_healthy`/`engines_warn`/`engines_fail` and `scan_activity`'s `sites_with_recent_scans`/`sites_total` (and any other non-`rules_*` keys present in 0.2.13 output).
4. **Every existing `RuleResult.summary` shape is preserved per rule_id.** E.g. `op.scan_activity.sites_overdue_scans.summary` continues to carry `count`/`sites_with_recent_scans`/`sites_total`.
5. **Read-only HTTP contract.** No new verbs; no `PUT`/`PATCH`/`DELETE`; no expansion of the POST allowlist.
6. **API call cost preserved.** `scan_activity` parses each site's scan response once; rules consume the parsed result. `scan_engines` makes one `GET /api/3/scan_engines` call. No new endpoints, no new pagination.

## Risks

- **Diff size.** This refactor touches 4 source files, 4 test files, and adds 14 rule classes. Mitigated by per-rule-class atomic commits where possible (each rule class lands in its own commit so reverts are surgical).
- **Drift-blob signature stability.** State-blob signatures key on `rule_id` plus message plus details. Any whitespace or punctuation drift in a rule's message construction breaks delta continuity for users carrying a prior-state file forward. Mitigated by the existing test message-string assertions and by the byte-identity invariant above.
- **Test migration surface.** `tests/checks/test_scan_engines.py` and `tests/checks/test_scan_activity.py` will need substantive rewrites (the flat-finding-list assertions don't survive the move to per-rule-result indexing). The implementation plan must allocate dedicated tasks for test migration before claiming a check's refactor is done.
- **`scan_activity.py` parsed-data layer.** Introducing `_ParsedScan` / `_ParsedSiteScans` is a real architectural choice: the rule methods become pure functions over the parsed data instead of doing their own iteration. This is desirable but is the largest local design change in the spec. If implementation reveals friction (e.g. one rule needs an unparsed field that wasn't lifted), the answer is to extend the parsed types -- not to revert to per-rule iteration.

## Out of scope (deferred or rejected)

- **No `EnvSnapshot` extension.** The audit-vs-op-check boundary stays clean; `_ParsedSiteScans` is file-scoped (rejected option A from brainstorm question 2).
- **No registry, no `Protocol`, no decorator** for op-check rule classes. Each check's `run()` instantiates rules explicitly. (Rejected options B and C from brainstorm question 6 -- overkill for op-checks.)
- **No new rules.** Concept set unchanged: 4 in `scan_engines`, 6 in `scan_activity`, 4 in `asset_coverage`, plus whatever `data_quality.py` has today.
- **No HTTP changes**, no `client.py` changes, no audit-subsystem changes.
- **No report-template / filter-bar changes.** Rule cards already render uniformly per rule_id; nothing on the rendering side needs to know that op-check rules are now classes.
- **No new config keys.** Threshold structure unchanged.
