# 0.2.12 — v3-spec alignment, helper extraction, dead-code removal

**Date:** 2026-05-06
**Target version:** 0.2.12
**Scope:** Single patch release bundling backlog items at versions 0.2.9, 0.2.12, and `someday`.
**Read-only invariant:** unchanged. No new HTTP verbs, no new POST paths, no `PUT`/`PATCH`/`DELETE`.

## Goal

Bring three op-check / audit-rule code paths back in line with the canonical Rapid7 v3
OpenAPI spec (`docs/research/api-v3.json`). All three are silently dead in production
today — tests pass only because fixtures use the same wrong field/enum shapes that the
production code reads. Bundle two adjacent low-risk improvements (cap-with-rollup helper
extraction in `asset_coverage.py`, removal of unused `EnvSnapshot.asset_has_agent`) into
the same release since they touch the same review surface and are equally read-only.

## Out of scope

- New scan-engine audit rules (engine-version, engine-OS) — backlog 0.2.4, deferred.
- Per-rule isolation refactor for `scan_engines.py` / `scan_activity.py` — backlog 0.3.0,
  needs its own spec.
- Identity-constants extraction across op-check rules — backlog 0.3.0, paired with the
  isolation refactor.

## Changes

### 1. `scan_engines.py` — fix dead status check

**File:** `src/rapid7_healthcheck/checks/scan_engines.py`

The current code flags `status == "inactive" or status == "unknown"` as fail. Per the
v3 spec, `ScanEngine.status` is `enum: [active, incompatible-version, not-responding,
pending-authorization, unknown]`. `inactive` is not a valid status — the branch is dead.

**Fix:** replace the `if` with a status-to-severity map:

```python
_BAD_STATUS_SEVERITY = {
    "incompatible-version": "fail",
    "not-responding":       "fail",
    "pending-authorization":"warn",
    "unknown":              "warn",
}
```

Each engine whose `status` is in this map produces a `bad_status_findings` entry with
the per-status severity. The `continue` after a bad-status finding is preserved (no
point checking `last_refreshed`/sites once the engine is known unreachable). The
`per_engine_worst` accumulator becomes severity-aware.

Rule identity unchanged: `op.scan_engines.bad_status`, `default_severity="fail"` (the
banner severity = highest severity any finding can carry under this rule). Rule name
and description updated to reference all four enum values; per-finding messages get a
short cause description per status (e.g. `"… status is 'incompatible-version' — engine
code is incompatible with this console; cannot scan"`).

**Severity rationale (per Q2 — option A):**

| Status | Severity | Reason |
|---|---|---|
| `incompatible-version` | fail | Engine cannot scan until upgraded. |
| `not-responding`       | fail | Console can't reach engine; scans blocked. |
| `pending-authorization`| warn | Setup-time transient state. |
| `unknown`              | warn | Indeterminate; matches existing rule intent. |

### 2. `scan_activity.py` — fix `_FAILED_STATUSES` and add unknown-scan rule

**File:** `src/rapid7_healthcheck/checks/scan_activity.py`

Two coupled changes:

**2a. Drop dead `"failed"`.** Per v3 spec, `ScanStatus` enum is `[aborted, unknown,
running, finished, stopped, error, paused, dispatched, integrating]`. `"failed"` is
not a member; the existing match is dead. New constant:

```python
_FAILED_STATUSES = {"aborted", "stopped", "error"}
```

**2b. New rule `op.scan_activity.recent_unknown_scans`** (Q4 — option C).

Within the per-site scan loop, accumulate a separate `unknown_recent_findings` bucket
for scans whose `status == "unknown"` and whose `start_time >= recent_cutoff`. Cap at
`_MAX_FAILED_FINDINGS=20` (matching the existing failed-scan pattern); on overflow,
emit one rollup finding the same way `recent_failed_scans` does.

New `RuleResult`, inserted right after `recent_failed_scans` in the `rule_results`
list:

- `rule_id`: `op.scan_activity.recent_unknown_scans`
- `rule_name`: `Recent scans in unknown state`
- `description`: *"Scans within the recent window whose status is reported as 'unknown'
  — indeterminate scan state, likely needs operator inspection."*
- `default_severity`: `warn`
- `sources`: `[_SRC_SCANS]`
- `summary`: `{"unknown_count": <int>}`

### 3. Audit rules — fix `scanEngineId` → `scanEngine`

**Files:**
- `src/rapid7_healthcheck/audit/rules/single_engine_overload.py`
- `src/rapid7_healthcheck/audit/rules/local_engine_production_scope.py`
- `tests/audit/rules/test_single_engine_overload.py`
- `tests/audit/rules/test_local_engine_production_scope.py`

Per v3 spec, `Site.scanEngine` is `integer` ("identifier of the scan engine configured
in the site"). There is no `scanEngineId` field. Both rules read the wrong key, so on
real consoles the engine→sites map is always empty and both rules always emit zero
findings.

**Fix (Q5 — option A):** read only `scanEngine`. No defensive `or "scanEngineId"`
fallback — the spec is unambiguous, and there is no evidence the phantom field ever
existed in any console version (zero matches outside these two rules and their tests).
If a real report surfaces an old console returning `scanEngineId`, follow up in a
0.2.13 patch.

**Both rules:** change `engine_id = site.get("scanEngineId")` → `engine_id =
site.get("scanEngine")`.

**Both test files:** replace every `"scanEngineId": <int>` in fixtures with
`"scanEngine": <int>`. Existing assertions pass unchanged because the rules' outputs
do not depend on the field name.

### 4. Extract `_capped_findings_with_rollup` in `asset_coverage.py`

**File:** `src/rapid7_healthcheck/checks/asset_coverage.py`

The cap-with-rollup pattern (head findings up to `_PER_ITEM_FINDING_CAP=500`, then one
overflow `Finding` with `remainder/total/cap` keys in `details`) appears in three
places:

1. `_per_asset_findings` (line 40) — already a helper, but only for assets.
2. Dead asset_groups loop (line 322) — inline.
3. Agent-only outsiders loop (line 535) — inline.

**Extract a single helper at module top, near `_PER_ITEM_FINDING_CAP`:**

```python
def _capped_findings_with_rollup(
    items: list,
    build_finding: Callable[[Any], Finding],
    severity: Severity,
    label: str,
    cap: int = _PER_ITEM_FINDING_CAP,
    rollup_details_extra: dict | None = None,
) -> list[Finding]:
    """Build per-item findings up to `cap`; append one rollup Finding for the
    remainder. `label` is the noun used in the rollup message ("+ N more
    <label>(s) (truncated; showing first <cap>)"). `rollup_details_extra` is
    merged into the rollup finding's `details` dict (alongside the canonical
    `remainder` / `total` / `cap` keys).
    """
```

**Rewrite all three call sites:**

1. `_per_asset_findings` becomes a thin wrapper that constructs an asset-specific
   `build_finding` closure and calls the helper. **Public signature preserved** so the
   existing callers at lines 176 and 218 do not change.
2. Dead asset_groups loop → single call (label="group").
3. Agent-only outsiders loop → single call (label="asset").

**Invariant:** finding messages and `details` shapes preserved byte-for-byte so
delta-blob signatures stay stable for unchanged underlying issues. Each call site
passes its current extra `details` keys via `rollup_details_extra`.

## Release

Single 0.2.12 patch release. CHANGELOG entry:

- **Fixed**
  - `op.scan_engines.bad_status` now matches the v3 `ScanEngine.status` enum
    (`incompatible-version`, `not-responding`, `pending-authorization`, `unknown`);
    the dead `inactive` branch is removed. `incompatible-version`/`not-responding`
    are flagged fail; `pending-authorization`/`unknown` flagged warn.
  - `op.scan_activity.recent_failed_scans` no longer matches the non-existent
    `"failed"` v3 status; the rule covers the real terminals
    `aborted`/`stopped`/`error`.
  - `single_engine_overload` and `local_engine_production_scope` audit rules now
    read the v3 `Site.scanEngine` field. Both were silently dead (always producing
    0 findings) where the console returns the spec-compliant field name.
- **Added**
  - New rule `op.scan_activity.recent_unknown_scans` (warn) — flags scans within
    the recent window reported as `unknown`-state.
- **Changed**
  - Internal: cap-with-rollup pattern in `asset_coverage.py` extracted to
    `_capped_findings_with_rollup`; three call sites collapsed to one helper. No
    user-visible change.
  - Internal: `EnvSnapshot.asset_has_agent` removed (zero production callers
    since 0.2.7).
- **Notes**
  - First post-upgrade run will mark some engines and scans as "Changed" in the
    delta blob because (a) some engine `unknown`-status findings shift from fail
    to warn, and (b) some scans newly appear in `recent_unknown_scans`. One-time
    only.

Tag `v0.2.12`, build zip `rapid7-insightvm-audit-0.2.12.zip`, GitHub release per

## Risks & mitigations

| Risk | Mitigation |
|---|---|
| Delta-blob churn on first post-upgrade run. | Documented in CHANGELOG **Notes** (one-time, mirrors 0.2.10 pattern for R4). |
| Phantom-field regression: ancient console returning `scanEngineId`. | Spec is unambiguous. If a real report surfaces, fix in 0.2.13 with `site.get("scanEngine") or site.get("scanEngineId")`. Don't preemptively defend unverified cases. |
