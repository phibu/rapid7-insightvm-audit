# 0.6.0 -- Backlog Burndown Design

**Date:** 2026-05-19
**Driver:** Clear the 0.6.0 backlog after the cloud-drift v0 cycle (0.5.0 + 0.5.1). No new user-facing features; correctness, hygiene, and documentation only.
**Predecessor:** 0.5.1 (`/api/3/agents` 504-mid-pagination fix + cloud-drift v0 polish).

## Scope

Nine items grouped into three buckets. Five feature items from the original 0.6.0 backlog (cursor pagination, paginate_post, verify_tls, parallel CloudSnapshot fetches, cross-batch concurrent pagination) are deferred to `someday` -- none have a rule pulling on them, building them speculatively grows surface without a user.

### Bucket 1: Correctness investigations (2 items)

#### Item 1 -- `EnvSnapshot.scan_engines()` pagination behavior

**Backlog claim:** `EnvSnapshot.scan_engines()` calls `client.get("/api/3/scan_engines")` without pagination, silently truncating to one page on consoles with >250 engines.

**Investigation outcome:** the v3 OpenAPI spec (`docs/research/api-v3.json`) shows `/api/3/scan_engines` has **no `parameters`** array and the response schema `CollectionModelScanEngine` has **no `page` field** (only `links` and `resources`). The endpoint is documented as an unpaginated collection. The user has not encountered consoles with >250 engines in real deployments, so the claim is unproven.

**Action:** add a pinning comment in `EnvSnapshot.scan_engines()` documenting the assumption -- "v3 spec shows no pagination params; if a future console returns a paginated envelope (response includes a `page` key), switch to `paginate()`. Until then, single GET is correct." Also correct the misleading comment in `audit/cloud_drift/snapshot.py:console_engines()` which claims it paginates to avoid "silent first-page-only truncation" -- that truncation cannot happen if the endpoint isn't paginated. The cloud-drift call to `paginate()` stays (paginate's page-0 fast path returns the full collection harmlessly when `totalPages` is absent), but the comment gets honest.

**No behavior change.** Investigation outcome is documentation.

#### Item 2 -- Cloud-drift `_extract_diagnostics` regex coverage

**Issue:** `cloud_client.py:_extract_diagnostics` regex matches only `/api/3/...` paths. Cloud-rule errors against `/v4/integration/...` produce empty `error_path` in failure findings.

**Action:**
1. Add a test pinning the current empty-path behavior on a `/v4/...` error.
2. Extend the regex to match both `/api/3/...` and `/v4/integration/...` (alternation).
3. Re-pin the test to assert the path is now populated for both shapes.

### Bucket 2: Mechanical correctness fixes (2 items)

#### Item 3 -- Engine cross-key fallback for `cd.scan_engine_cloud_registration`

**Issue:** the rule cross-matches v3 console engines to v4 cloud engines by `name` only. If the same physical engine is registered under different names on the two sides (e.g. after a rename on one side), it appears "missing from cloud."

**Action:** add a fallback matcher. When the primary `console.name == cloud.name` lookup misses, try **`console.address == cloud.host_name`** (cross-API comparison):
- v3 console engine record exposes `address` (per v3 spec).
- v4 cloud engine record exposes `host_name` (per v4 spec).

**Matching precedence:** name match always wins. If name misses, try fallback. If fallback matches one cloud entry, use it and log INFO (`"matched engine X via host_name fallback, primary name match failed"`). If neither matches, the engine stays flagged as "missing from cloud" (today's behavior).

**README:** document the degraded mode under the cloud-drift section -- primary key is name, fallback is host_name/address, name renames on one side without the other still get caught.

**Edge cases pinned by tests:**
- Engine in console with `name=null` but valid `address` -- falls through to fallback.
- Engine in cloud with `host_name=null` -- fallback can't match, primary name wins or "missing" stands.
- Both primary name and fallback would match but to different cloud entries -- name wins (it's the primary key); pinned in test.

**Risk:** changes which engines get flagged on real deployments. The change can only **reduce** false positives (more engines match successfully), never **introduce** false positives (no engine can newly become "missing from cloud" -- the fallback is additive). Worst case is a previously-flagged engine no longer flagged, which is the correct behavior.

#### Item 4 -- Silently-skipped-rules-when-cloud-empty footgun

**Issue:** when `cloud_integration.enabled = true` but `cloud_drift.rules:` is absent or empty in `config.yaml`, every rule falls into the `rule_cfg is None` branch and is silently skipped. The user sees a green report with no cloud-drift findings and assumes everything passed.

**Action:** in `CloudDriftAuditCheck.run()`, at orchestrator startup (before the rule loop), if `cloud_integration.enabled = true` AND the rule-config dict is empty, log a single `logger.info()` line:

```
cloud_integration is enabled but no cloud_drift rules are configured;
every cloud-drift rule will be skipped. Add a `cloud_drift.rules:` block
to config.yaml to enable rules.
```

**No finding emitted, no status change.** Pure operator feedback. The report still renders identically -- only the log line is new.

**Test:** mock the orchestrator config to enabled-but-empty-rules and assert the INFO log fires. Test the inverse cases (disabled, or enabled-with-rules) and assert no log fires.

### Bucket 3: Hygiene + docs (5 items)

#### Item 5 -- `_ensure_default_on(checks, *names)` helper

**Issue:** `config.py:_build_app_config` has three back-to-back default-on blocks for `configuration_audit`, `user_permission_audit`, `cloud_drift_audit` -- identical shape, copy-pasted.

**Action:** extract to a single helper:

```python
def _ensure_default_on(checks: dict, *names: str) -> None:
    """Ensure each named check has an entry in `checks` with `enabled: True`
    unless the user has explicitly set `enabled: False`."""
    for name in names:
        if name not in checks:
            checks[name] = {"enabled": True}
```

**Critical test:** user-set `enabled: false` must be preserved (the helper only fills missing entries; it never overwrites explicit values).

#### Item 6 -- Drop `_CLOUD_FULL_SCAN` / `_CLOUD_SAMPLE_SIZE` constants

**Decision:** drop them and pass literals in `audit/cloud_drift/__init__.py`. The existing comment ("they exist for Rule protocol compatibility") explains the no-op purpose; the indirection adds nothing. Replace with literal values at the two call sites + a brief inline comment.

#### Item 7 -- Kwarg-only `progress` on `CloudDriftAuditCheck.run`

**Issue:** `CloudDriftAuditCheck.run` accepts `progress` as positional-or-keyword while `ConfigurationAuditCheck.run` and `UserPermissionAuditCheck.run` both accept it kwarg-only (`*, progress=...`).

**Action:** add the `*` to the signature. Caller in `__main__.py` already passes `progress=` by keyword, so no caller change required. Tests that pass positionally need updating (audit and re-run).

#### Item 8 -- Direct cloud-drift config-validator tests

**Issue:** the shared validator path covers rule-body shape errors (non-mapping body, missing `enabled`, non-bool `enabled`), but `tests/test_config_cloud_drift.py` doesn't pin them specifically for `cloud_drift`. If the validator path ever diverges (e.g. a cloud-drift-specific validator gets added), the regression would slip.

**Action:** add direct tests in `tests/test_config_cloud_drift.py`:
- Rule body that's a string, list, or int (not a dict) → expect `ConfigError`.
- Rule body dict missing the `enabled` key → expect `ConfigError`.
- Rule body with `enabled: "true"` (string) → expect `ConfigError`.
- Rule body with `enabled: 1` (int) → expect `ConfigError`.

#### Item 9 -- Info-severity convention docs

**Issue:** `_rollup_audit_status` only escalates on `warn`/`fail`. A `severity="info"` config override produces a finding but the check stays `pass`. Every existing rule shares this convention. The backlog flagged this as ambiguous.

**Decision:** keep current behavior; document it explicitly. `info` is a default-severity for skip/diagnostic paths, never a status escalator.

**Action:**
- Add one paragraph to `CLAUDE.md` under "Severity and exit code semantics" stating that `info` findings never escalate status and explaining why (info is for context, not problems).
- Add one paragraph to README under the audit rules section so users configuring `severity: info` overrides understand the rollup contract.

**No code change.**

## Implementation order

Each step lands as one commit on a single feature branch (`feature/0.6.0-backlog-burndown`). Order chosen to land low-risk doc items first and build momentum, with the largest behavior change last:

1. **#6** -- drop `_CLOUD_FULL_SCAN` / `_CLOUD_SAMPLE_SIZE` constants (mechanical).
2. **#7** -- kwarg-only `progress` on `CloudDriftAuditCheck.run` (mechanical).
3. **#9** -- info-severity docs in CLAUDE.md and README (doc-only).
4. **#5** -- extract `_ensure_default_on` helper + test that user-disable is preserved.
5. **#1** -- `EnvSnapshot.scan_engines()` pinning comment + cloud-drift snapshot comment correction.
6. **#2** -- `_extract_diagnostics` regex extension + tests.
7. **#4** -- INFO log when cloud enabled but rules empty + tests.
8. **#8** -- direct cloud-drift validator tests.
9. **#3** -- engine cross-key fallback + tests + README degraded-mode note.
10. **Release ceremony** -- CHANGELOG, version bump, backlog cleanup, commit on main, tag v0.6.0, build zip, gh release create.

## Error handling

- **#3:** when name and fallback both fail, behavior matches today ("missing from cloud"). When only fallback matches, log INFO so users see why a previously-flagged engine is now matched.
- **#4:** fires once at orchestrator startup, not per-rule. Pure operator feedback, no finding.
- **#2:** if neither regex branch matches, fall back to current empty-path behavior. No new failure mode.

## Edge cases pinned by tests

- **#3 -- fallback matching:**
  - Engine in console with `name=null` but valid `address` -- falls through to fallback.
  - Engine in cloud with `host_name=null` -- fallback can't match.
  - Both primary name and fallback would match different cloud entries -- name wins.
- **#4 -- INFO log:**
  - `cloud_integration.enabled=false` (default) -- no log line.
  - `cloud_integration.enabled=true` AND rules present -- no log line.
  - Only enabled-but-empty triggers.
- **#5 -- `_ensure_default_on`:**
  - User-set `enabled: false` preserved.
  - Missing entry defaults to `enabled: true`.
  - Existing `enabled: true` left alone.
- **#8 -- validator:**
  - Non-mapping rule body (string, list, int).
  - Missing `enabled` key.
  - Non-bool `enabled` (`"true"`, `1`).

## Risks

- **Highest risk: item #3.** Introduces a new matching code path. Mitigated by: (a) name match always wins, so the change is purely additive -- no previously-passing engine can newly become "missing"; (b) tests pinning all three precedence cases; (c) INFO log so users can audit fallback matches in their logs.
- **Medium risk: item #1.** Investigation outcome is "no code change," but if real-world data later shows truncation _does_ happen (Rapid7 spec drift), the rules calling `scan_engines()` (`local_engine_production_scope`, `single_engine_overload`, `engine_version_drift`) will continue to silently false-positive. Mitigated by the pinning comment explicitly naming this signal ("if response includes a `page` key, switch to paginate") so a future debugger finds the fix path quickly.
- **Low risk: everything else.** Mechanical, well-bounded, individually small.
