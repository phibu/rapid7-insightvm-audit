# 0.7.0 — Rule-Card Streamline + Cleanups

**Date:** 2026-05-26
**Type:** Minor release (feature + cleanups)
**Branch:** `release/0.7.0`

## Motivation

The biggest item from the 0.6.5 user-feedback batch was a request to streamline the per-rule info bar in the report. Today every rule has its own bespoke `summary` shape — `count`, `stale_count`, `templates_examined/templates_flagged`, `engines_examined/engines_flagged`, `users_examined/users_flagged`, etc. The report template can't render a uniform "N examined, M passed, K failed" header because the data lives under different keys.

This release standardizes that as `card_summary: dict[str, int] | None` on `RuleResult`, with the template rendering `examined / passed / failed` uniformly when present. Rules where "examined" is genuinely ambiguous (question-style: console-vs-cloud asset-count drift, etc.) leave `card_summary=None` and the template falls back to today's per-key rendering.

Bundled with three cleanups from the 0.6.5/0.6.5.2/0.6.6 review backlog — none would justify their own release but they share architectural surface with F1.

## Task-by-task design

### C3 — `duration_ms: int | None` contract

**Files touched:**
- `src/rapid7_healthcheck/audit/__init__.py` (`RuleResult` dataclass at ~line 50; the direct-stamp pattern at line 154)
- `src/rapid7_healthcheck/checks/_op_rule.py` (`safe_run` guard at lines 144-164; `make_rule_result` signature)
- `src/rapid7_healthcheck/report.py` (`_metrics` aggregation: search for `if r.duration_ms`)
- Tests that assert `duration_ms == 0` or use `duration_ms` defaults

**The change:**
- `RuleResult.duration_ms: int = 0` → `int | None = None`.
- `make_rule_result(..., duration_ms: int = 0)` → `int | None = None`.
- `safe_run` success path: `if result.duration_ms == 0:` → `if result.duration_ms is None:`.
- `report.py:_metrics` `if r.duration_ms:` (truthy check — 0 and None both treated as "absent") works correctly for both states since both are falsy. No code change required, but verify.
- Audit orchestrator at `audit/__init__.py:154` directly assigns `result.duration_ms = int(...)` after timing. This sets the field to an int (not None). Behavior unchanged. **Important:** the audit orchestrator runs `try/except` around each rule's execution and stamps `duration_ms` on the returned result. The current pattern relies on direct mutation. Since `RuleResult` is a `@dataclass` (mutable), this works regardless of the field's default. Verify.

**Backward-compat for tests.** Any test asserting `result.duration_ms == 0` after a rule path that doesn't set timing will need updating to `result.duration_ms is None`. Sweep the test suite. Realistically: only tests that construct `RuleResult(...)` directly and don't pass `duration_ms` would still see the default value.

**Verification (TDD):**
- New test: `make_rule_result(...)` without `duration_ms` produces `duration_ms=None`.
- New test: `safe_run(fn)` where `fn` returns a rule with `duration_ms=None` stamps a measured int.
- New test: `safe_run(fn)` where `fn` returns a rule with `duration_ms=0` (explicit) **preserves the 0** (don't overwrite — "measured zero" is now an explicit signal).
- Existing tests: 746+ baseline must remain green. Watch for tests asserting `r.duration_ms == 0` that need updating to `is None`.

**Why this matters for F1.** `_metrics` aggregates `total_duration_ms = sum(r.duration_ms for r in ... if r.duration_ms)`. The `if r.duration_ms` filter works correctly for both `0` and `None` (both falsy). No template change required for C3.

### C1 — Split dual-knob negative test

**File:** `tests/audit/rules/test_scan_report_schedule_overlap.py:235`

Existing test `test_assumed_durations_floored_at_one_minute_when_negative` sets both knobs to -5 and asserts findings emitted. If a future regression breaks only ONE knob's guard, the other knob keeps the window open and the test still passes.

- `test_assumed_scan_duration_floored_at_one_minute_when_negative` — `assumed_scan_duration_minutes: -5`, `assumed_report_duration_minutes: 30` (good). Assert finding.

Delete the original combined test.

### C2 — Gateway-error handling on `scan_engine_pools`

**File:** `src/rapid7_healthcheck/audit/snapshot.py` (`scan_engine_pools` method)

Currently handles 404 only. `agent_count()` at lines 644-680 is the established pattern — also handles 502/503/504 and pre-response failures (`status_code is None`) for endpoints where gateway timeouts are a real risk.

**Fix:** mirror `agent_count()`'s broader trap:
```python
def scan_engine_pools(self) -> list[dict]:
    if self._scan_engine_pools is None:
        try:
            body = self._client.get("/api/3/scan_engine_pools")
            self._scan_engine_pools = list(body.get("resources", []))
        except Rapid7ClientError as e:
            if e.status_code == 404:
                logger.info("scan_engine_pools endpoint not available")
                self._scan_engine_pools = []
            elif e.status_code is None or e.status_code in (502, 503, 504):
                logger.warning(
                    "scan_engine_pools endpoint unreachable (gateway error "
                    "or network error); EngineUnpairedRule will fall back "
                    "to direct-only pairing: %s", e,
                )
                self._scan_engine_pools = []
            else:
                raise
    return self._scan_engine_pools
```

**Why this is independent of the outer `try/except Exception`.** `ScanEnginesCheck.run` already wraps `snapshot.scan_engine_pools()` in a broad catch and falls back to an empty index. End-to-end behavior doesn't change. But the snapshot-level trap is more informative (the log message tells the user which endpoint failed, why, and what fallback ran), and matches the established `agent_count()` pattern.

**TDD:** new tests for the three new branches (502/503/504/None) — each returns `[]`, each logs at WARNING level.

### F1 — Rule-card streamline (the flagship)

**The data shape.** Add `card_summary: dict[str, int] | None = None` to `RuleResult` in `audit/__init__.py`:

```python
@dataclass
class RuleResult:
    # ... existing fields ...
    card_summary: dict[str, int] | None = None
```

When present, the dict has exactly three keys: `"examined"`, `"passed"`, `"failed"`. Type is `int` for each. The template renders `<N> examined · <P> passed · <K> failed` uniformly in the rule card header (or however the existing card header is structured — research the template).

**When to set `card_summary`.** A rule populates it when it has a meaningful per-item population it examines (e.g. "looked at 12 sites, 9 passed, 3 failed"). Rules where "examined" is genuinely ambiguous leave it None.

**Helper for op-checks.** Extend `make_rule_result(...)` in `_op_rule.py`:

```python
def make_rule_result(
    *,
    # existing kwargs...
    examined: int | None = None,
) -> RuleResult:
    # existing logic...
    card_summary: dict[str, int] | None = None
    if examined is not None:
        # findings carry severity per item — pass = no finding, fail = finding emitted
        # But: a single rule may produce a finding per item (e.g. unpaired engines emit one per)
        #      OR an aggregate "N stale assets" finding (one finding, N items).
        # The honest derivation requires the rule to tell us how many it found bad.
        ...
    return RuleResult(..., card_summary=card_summary)
```

Wait — this is the architectural rub. The "passed/failed" derivation can't come from `findings` alone because some rules emit one finding-per-item (op.scan_engines.unpaired) while others emit one aggregate finding (op.data_quality.missing_os, where one finding represents N items).

**Resolution.** Make the helper take `examined` + `failed` explicitly (the rule knows its own arithmetic). Derive `passed = examined - failed`:

```python
def make_rule_result(
    *,
    # existing kwargs...
    examined: int | None = None,
    failed: int | None = None,
) -> RuleResult:
    card_summary: dict[str, int] | None = None
    if examined is not None and failed is not None:
        card_summary = {
            "examined": examined,
            "passed": max(0, examined - failed),
            "failed": failed,
        }
    # ... existing logic, pass card_summary into RuleResult(...)
```

`max(0, ...)` guards against `failed > examined` (programming bug, but better not to render negative numbers).

**Audit rules** build `RuleResult(...)` directly. Each audit rule constructs `card_summary` inline (or omits it) — same shape, no helper needed since the audit-rule constructor surface is already verbose. Example:

```python
# audit/rules/single_engine_overload.py (currently has engines_examined / engines_flagged)
return RuleResult(
    # ... existing fields ...
    summary={"engines_examined": len(sites_by_engine), "engines_flagged": engines_flagged},
    card_summary={
        "examined": len(sites_by_engine),
        "passed": len(sites_by_engine) - engines_flagged,
        "failed": engines_flagged,
    },
)
```
