## Task 1 (C3): `duration_ms: int | None` contract

### Context for implementer

**Current state.** `RuleResult.duration_ms: int = 0` (declared in `src/rapid7_healthcheck/audit/__init__.py`). The value `0` is overloaded — it can mean "not measured" (rule didn't time itself) or "measured zero" (rule ran in under 1 ms). The 0.6.5.2 fix to `safe_run` uses `if result.duration_ms == 0:` as a sentinel for "not measured", which works today but is ambiguous and would break if a rule ever wanted to record a genuine sub-millisecond timing as `0`.

**The change.** Switch the type to `int | None = None`. None means "not measured", 0 means "measured zero" (explicit).

### Files to touch

1. **`src/rapid7_healthcheck/audit/__init__.py`** — `RuleResult` dataclass. Change `duration_ms: int = 0` → `int | None = None`.
2. **`src/rapid7_healthcheck/checks/_op_rule.py`** — three things:
   - `make_rule_result(..., duration_ms: int = 0)` → `int | None = None`
   - `error_rule(..., duration_ms: int = 0)` → `int | None = None`
   - `safe_run` success-path guard: `if result.duration_ms == 0:` → `if result.duration_ms is None:`
3. **`src/rapid7_healthcheck/audit/__init__.py`** — find the direct-stamp pattern (search for `duration_ms =`). The audit orchestrator times each rule and assigns `result.duration_ms = int(...)`. No change needed — assigning a real int after timing works for both `int = 0` and `int | None = None`. **Verify this by reading the surrounding code.**
4. **`src/rapid7_healthcheck/report.py`** — search for `r.duration_ms` and `duration_ms`. The `_metrics` aggregation uses `if r.duration_ms:` truthy check, which works for both `0` and `None` (both falsy). **No code change should be required.** Verify by reading and running tests.
5. **Tests** — sweep for `duration_ms == 0` assertions:
   ```
   Grep tool: pattern "duration_ms\s*==\s*0|duration_ms=0", path "tests/", output_mode "content", -n true
   ```
   For each match, decide: does the test assert "not measured" (update to `is None`) or "measured zero" (keep as `== 0`)? Most will be "not measured" cases.

## Task 3 (C2): `scan_engine_pools` gateway handling

### Context

`src/rapid7_healthcheck/audit/snapshot.py:scan_engine_pools` traps 404 only. `agent_count()` at lines 644-680 is the established pattern for endpoints prone to gateway errors — it also traps 502/503/504 and pre-response failures (`status_code is None`). 0.6.5.2 review surfaced the inconsistency. End-to-end behavior unchanged (the outer `try/except Exception` in `ScanEnginesCheck.run` already absorbed these), but the snapshot-level trap produces a more informative log message and matches the established pattern.

### What to implement

Edit `src/rapid7_healthcheck/audit/snapshot.py` `scan_engine_pools` method:

```python
def scan_engine_pools(self) -> list[dict]:
    """Return all scan engine pools from /api/3/scan_engine_pools.

    Used to detect pool-mediated site assignments — see EngineUnpairedRule.
    Single GET, no pagination.

    Returns ``[]`` on:
        - 404 (older console without pool support);
        - 502 / 503 / 504 or pre-response failure (status_code is None) —
          gateway-level transient failures. The downstream rule falls back
          to direct-only pairing, which is the 0.6.5 behavior, so an
          unreachable endpoint produces a partial-but-correct result
          rather than an error rule.

    Other Rapid7ClientError responses propagate.
    """
    if self._scan_engine_pools is None:
        try:
            body = self._client.get("/api/3/scan_engine_pools")
            self._scan_engine_pools = list(body.get("resources", []))
        except Rapid7ClientError as e:
            if e.status_code == 404:
                logger.info("scan_engine_pools endpoint not available")
                self._scan_engine_pools = []
            elif e.status_code is None or e.status_code in (502, 503, 504):
                logger.warning(
                    "scan_engine_pools endpoint unreachable (gateway error "
                    "or network error); EngineUnpairedRule will fall back "
                    "to direct-only pairing: %s", e,
                )
                self._scan_engine_pools = []
            else:
                raise
    return self._scan_engine_pools
```

## Task 4 (F1): Rule-card streamline (the flagship)

### Context for implementer

**Goal.** Add a standardized `card_summary: dict[str, int] | None` field to `RuleResult` carrying three canonical counts: `examined`, `passed`, `failed`. The Jinja template renders these uniformly in the rule card header when present. Rules where "examined" is genuinely ambiguous (ratio questions, single-entity rules) leave `card_summary=None` and the template falls back to today's per-key rendering.

**Why now.** Top item from 0.6.5 user feedback. Deferred from 0.6.6 because the delta-blob compatibility story needed care.

**Critical: do NOT modify `summary`.** The existing `RuleResult.summary` dict stays exactly as-is. The delta-blob projection (`report.py:_state_blob_projection` and `_compute_delta`) reads `summary` and must continue to work against 0.6.x blobs. The new `card_summary` is purely additive.

### Step 1 — Add the field

In `src/rapid7_healthcheck/audit/__init__.py`, find `RuleResult`. Add a new field:

```python
@dataclass
class RuleResult:
    # ... existing fields ...
    card_summary: dict[str, int] | None = None
```

Place it near `summary` for readability. Update the docstring/comment to describe the contract:

> `card_summary` (optional) — three canonical counts the report renders uniformly in the rule card header: `{"examined": int, "passed": int, "failed": int}`. Set when the rule has a meaningful per-item population it examined; leave None for rules where "examined" is genuinely ambiguous (ratio questions, single-entity questions).

### Step 2 — Extend `make_rule_result`

In `src/rapid7_healthcheck/checks/_op_rule.py`, extend `make_rule_result(...)`:
