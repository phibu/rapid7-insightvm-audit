# Rapid7 InsightVM Health-Check

Domain and architecture language for the read-only audit tool that runs against InsightVM Security Consoles and the InsightVM Cloud. Terms here are the agreed vocabulary; use them exactly and avoid the listed synonyms.

## The two Rapid7 APIs

**Console API (v3)**:
The on-prem Security Console REST API under `/api/3/...`. Responses wrap results in `{resources, page}`, with `page.totalPages` driving pagination. Auth is HTTP Basic only (the Console does not accept `X-Api-Key` -- that is the v4 Cloud API's mechanism).
_Avoid_: "the main API", "the REST API" (ambiguous -- there are two).

**Cloud Integrations API (v4)**:
The InsightVM Cloud API under `/v4/integration/...`. Responses wrap results in `{data, metadata, links}`, with `metadata.totalPages` driving pagination. Auth is `X-Api-Key` only.
_Avoid_: "the cloud endpoint", "the v4 endpoint" (it is an API surface, not one endpoint).

## Templates

**Scan template**:
A reusable scan-configuration object on the Security Console (`/api/3/scan_templates`) carrying the ~50 tunable settings that govern how a scan runs -- checks, discovery, service discovery, performance, web, policy, database, telnet. This is the *only* template the Template Configuration Audit examines. When this glossary or a rule says "template" unqualified, it means a scan template.
_Avoid_: bare "template" in code or docs that touch report templates; "scan config" (that is the per-site binding, not the reusable object).

**Report template**:
A separate reusable object (`/api/3/report_templates`) governing report *layout and content*, unrelated to how scans run. Currently **un-audited** by this tool. Named here only to keep it distinct from a scan template -- the two share the word "template" and nothing else.
_Avoid_: calling this a "template" without the "report" qualifier when a scan template is also in scope.

**Asset discovery vs. service discovery** (two distinct phases of a scan):
*Asset discovery* answers "is a host alive here?" -- its ports live at `discovery.asset.tcpPorts` / `udpPorts` (integer arrays, default empty: discovery falls back to ICMP/ARP). *Service discovery* answers "what's listening on a live host?" -- its ports live at `discovery.service.tcp` / `udp`, each a `{ports, additionalPorts, excludedPorts}` object of **string** fields where `ports` defaults to `"well-known"` (other values: `"all"`, `"none"`, explicit lists/ranges). The two are independent: a template may disable asset-discovery packets (the operator already knows the targets are live) while service discovery scans `"well-known"` ports normally. A rule reasoning about "discovery ports" **must** say which phase -- conflating them was the #31 false positive (the `service_discovery_disabled` rule read the *asset* subtree). "Service discovery disabled" is only true when **both** `service.tcp` and `service.udp` have an empty effective port set (`ports` ∈ {`""`, `"none"`} *and* empty `additionalPorts`); a `"well-known"` default is never "disabled".
_Avoid_: bare "discovery ports" (say "asset-discovery ports" or "service-discovery ports"); treating asset-discovery being off as service discovery being off.

**Effective check set** (what a scan template actually assesses):
The set of vulnerability checks a scan runs is **not** the `checks.categories.enabled` / `checks.types.enabled` lists read literally -- it is computed by Rapid7's *enable-minus-disable* model (per the `ScanTemplateVulnerabilityChecks` schema): enabled categories/types are included, their `disabled` lists removed, `individual.enabled` checks added (even if their category was disabled), `individual.disabled` removed, then the `unsafe` / `potential` booleans filter. Crucially the **baseline is unknown from the template JSON** -- an empty `categories.enabled` does *not* mean "no categories"; the common pattern is "all categories on by default, a few in `disabled`". So the tool **cannot compute "this template produces zero findings" from the object alone** -- it can only prove the weaker "nobody configured any checks" when *every* list is empty (`categories.enabled`+`disabled`, `types.enabled`+`disabled`, and `individual.enabled` all empty). That provably-blank case is the only honest signal (a `warn`, not a `fail` -- we can't claim zero findings, only an unconfigured-looking template). This was the #29 false positive: the rule read only the two `.enabled` lists and missed a template configured entirely via `disabled` lists + `individual.enabled`.
_Avoid_: "no checks selected" / "no checks enabled" inferred from empty `.enabled` lists alone (the disabled-lists and individual checks also enable coverage); claiming a template "will produce no findings" (the unknown baseline makes that unprovable -- say "no check configuration is present").

**Built-in scan template**:
One of the ~15 default scan templates Rapid7 ships (full audit, exhaustive, discovery, denial of service, the compliance audits, …; the canonical list is the [scan-templates appendix](https://docs.rapid7.com/insightvm/scan-templates/)). An operator **cannot edit** a built-in -- to change how it scans they clone it and edit the clone. The Template Configuration Audit still **audits** built-ins (a built-in bound to a live site can still scan badly) but **labels** any finding against one as built-in, with clone-and-rebind remediation guidance -- it does not exclude them by default (see [docs/adr/0003-audit-builtin-templates-but-label-them.md]). Detection is by **known ID** (`is_builtin_template` against a hardcoded frozenset of documented built-in slugs) -- the v3 `ScanTemplate` object carries no built-in flag, and an ID-*shape* test fails because user templates also get kebab-slug IDs.
_Avoid_: "default template" used loosely to mean "the template a site falls back to" (that is the *site's bound* template, which may itself be built-in or custom -- say "built-in template" for the Rapid7-shipped object); "system template", "read-only template" as the canonical noun (they describe the *consequence*, not the object -- the noun is "built-in scan template"); inferring built-in status from anything but the known-ID set.

## Asset coverage

**Agent site**:
The single site Rapid7 auto-assigns every Insight-Agent-reporting asset to -- its name defaults to **"Rapid7 Insight Agents"** (deterministic name, but the site **id varies** per console, so match by name, never by a hardcoded id). Distinct from a *scan(-engine) site*, which an operator configures with `included_targets` and a scan engine. An asset can live in both.
_Avoid_: "the agent site id" as a constant (it is per-console -- resolve it by name); conflating it with a scan site.

**Agent-site membership** (the canonical proxy for "has an Insight Agent"):
"This asset has an Insight Agent" is determined by **membership in the agent site**, *not* by presence in the `/api/3/agents` inventory. The two converge in practice (an agent-reporting asset is auto-assigned to the agent site) but the membership form is the one the tool uses, because it is the only one expressible in a server-side `assets/search` query -- there is **no agent filter field** on `assets/search` (the field list has `site-id` but nothing for "agent-managed"). Both agent-aware rules (`op.asset_coverage.agent_only_assets` and `agent_unauth_collision`) key on agent-site membership for this reason (see ADR-0004, ADR-0006). The accepted imprecision: a non-agent asset hand-added to the agent site, or an agent asset whose first sync hasn't auto-assigned it yet, is mis-classified -- both rare and transient.
_Avoid_: defining "agent-managed" as "in `/api/3/agents`" for a rule that must run server-side (that inventory cannot be intersected server-side -- only the agent *site* can); calling agent-site membership an approximation that needs a sampled cross-check (it is the definition, used exactly).

**Server-side membership query** (the technique):
The pattern that replaces per-asset iteration with one `assets/search` call whose answer is read from `page.totalResources` (zero asset bodies fetched). Asset-membership questions phrased over *sites* -- "are these two sites' asset sets disjoint?", "is an asset in site A but no site in set B?" -- become `match: all` filters on `site-id` (`in` / `not-in`), with the count taken from the result metadata. A rule that loops `iter_site_assets` and tests each asset is a candidate for this rewrite **iff its question is expressible with the `assets/search` filter fields** (site-id, host-name, ip-address, last-scan-date, operating-system, software, tags, CVE/CVSS -- but *not* agent-membership, credentials, or users). Rules whose cost comes from per-*credential* or per-*user* GETs cannot use it (those endpoints have no server-side aggregation).
_Avoid_: assuming any sampled/expensive rule can be made server-side (only asset-membership questions over `assets/search`-supported fields qualify); calling the resulting count a sample (it is exact).

**Agent-only coverage gap**:
The set of assets that belong to the **agent site** but to **no scan site** -- i.e. assets the console only ever sees through the endpoint agent, never via a network scan. This is a *site-membership* question (`agent_site_assets - union(scan_site_assets)`), **not** a scan-*scope* question (whether an asset's IP falls in some site's `included_targets`) -- the two give different numbers, and the membership definition is the canonical one (see [docs/adr/0004-agent-only-coverage-gap-server-side.md]). It is computed via a [[Server-side membership query]] -- complete and exact (`assets/search` `site-id in [agent] and not-in [scan sites]`, count from `page.totalResources`), never by sampling-and-extrapolating; the old sampled rule existed only to dodge a per-asset-GET loop the query removes.
_Avoid_: "agents outside scan scope" / "IP not in included_targets" as the definition (that is the dropped scope proxy -- the gap is by site membership); describing this count as an estimate or sample (it is exact).

**HttpTransport**:
The single deep module that owns everything identical across both APIs -- the retry loop, backoff, `Retry-After` handling, the read-only verb/path allowlist *enforcement*, JSON parsing, and the page-0-probe-then-batch pagination machinery. It learns the per-API differences from an injected `ApiDialect`.
_Avoid_: "base client", "HTTP helper", "the requests wrapper".

**ApiDialect**:
The small value object injected into an `HttpTransport` that carries the only things that differ between the Console API (v3) and the Cloud Integrations API (v4): the response envelope keys, the POST allowlist contents, the failure exception class, and the auth-error hint. It is the adapter at the transport's seam -- pure data, no behaviour.
_Avoid_: "config", "options", "profile" (those imply tuning knobs; a dialect is the API's fixed shape).

**Rapid7Client / CloudClient**:
The two thin adapters callers construct. Each is an `HttpTransport` wired with its `ApiDialect` (v3 and v4 respectively) and the auth its API accepts. They add no behaviour beyond construction; all transport logic is inherited from `HttpTransport`.
_Avoid_: "the v3 client / v4 client object" when you mean the class -- use the class names.

## Audit orchestration

**Audit category**:
One of the four parallel audit verticals -- Configuration Audit, Template Configuration Audit, User & Permission Audit, Cloud Drift Audit. Each owns a rule registry, a config block, and a `Check` class, but all four run their rules through the same loop.
_Avoid_: "audit type", "audit module", "audit subsystem" (use "category").

**AuditRunner**:
The single deep module that owns everything identical across the four audit categories -- the enabled-skip envelope, the per-rule enable/skip cards, the progress step/done choreography, per-rule timing, the exception trap (`_extract_diagnostics` → error `RuleResult`), the status rollup, and the `rules_*` summary counts. It learns the per-category differences from an injected `AuditCategory`. Analogous to `HttpTransport`: one loop, many categories.
_Avoid_: "audit engine", "audit loop", "base orchestrator".

**AuditCategory**:
The descriptor value object injected into the `AuditRunner` that carries the only things differing between the four categories: identity (`name`/`description`/`progress_prefix`), the rule `registry`, the `rules_config` accessor, the sampling args (`full_scan`/`sample_size`) forwarded to each rule, and three callables -- `gate` (enabled? plus the rich skip Finding), `build_snapshot` (pure snapshot construction), and an optional `prime` (an I/O early-exit, e.g. User & Permission's `/api/3/users` 404 self-skip). It is the adapter at the runner's seam -- mostly data, with the irreducible per-category behaviour held in the three callables.
_Avoid_: "audit descriptor", "audit spec", "audit profile", "audit config" (it is not the YAML config block).

**The four check classes** (`ConfigurationAuditCheck`, `TemplateAuditCheck`, `UserPermissionAuditCheck`, `CloudDriftAuditCheck`):
The thin `Check` adapters `__main__` registers. Each supplies an `AuditCategory` and delegates to the `AuditRunner`; they add no loop logic. Analogous to `Rapid7Client`/`CloudClient` wiring an `ApiDialect` into an `HttpTransport`.
_Avoid_: "audit orchestrator" for these -- the orchestrator is the `AuditRunner`; these are suppliers.

**build_env_snapshot**:
The single builder that maps a sampling config (`full_scan` / `sample_size`, duck-typed across `AuditConfig` / `TemplateAuditConfig`) plus an agents timeout onto a constructed `EnvSnapshot`. The one place that knows the snapshot's construction kwargs and the `DEFAULT_AGENTS_TIMEOUT` default -- covering the `EnvSnapshot` construction sites: `__main__` (for the operational checks and the Configuration audit's shared snapshot) plus the Template audit category. Because the timeout default lives once in the builder, the Template category -- whose config block lacks an `agents_timeout_seconds` field -- cannot drift to a stray hardcoded literal; the field is added to that block only if a Template rule ever needs a tuned timeout. The User & Permission category does **not** use this builder: it constructs a `UserSnapshot` (see below), which carries no sampling and no agents timeout.
_Avoid_: "snapshot factory", "make_snapshot".

**Cached accessor** (`_cached` / `_cached_by`, the snapshot's internal cache seam):
`EnvSnapshot`'s fetch-once-cache-return mechanism, owned in two private helpers rather than re-spelled per accessor. `_cached(slot, fetch)` is the single-value cache (the slot starts `None`, holds the fetched value after); `_cached_by(key, cache, fetch)` is the per-id cache (one entry per site/template id). The division is the depth boundary: **caching is uniform; fetching is not** -- the body each accessor turns into its cached value varies (paginate, get-plus-`resources`, the nested-`properties` guard, a `page.totalResources` int), so each accessor passes a `fetch` closure that owns its own envelope logic while the helper owns only the `is None` / `not in` check. The ~13 plain accessors route through these; what stays hand-rolled is deliberate -- the **error-policy** accessors (`scan_engine_pools`, `agents`, `agent_count`, `asset_group_member_count`: per-accessor 404/gateway `try`/`except` + flag-setting) carry irreducible per-accessor behaviour a cache helper must not flatten. The **sampling** decision -- `full_scan ? whole iterator : islice(sample_size)` -- is itself owned in one reducer, `_sampled(it)`, the third helper at this seam: both sampling accessors (`asset_sample`, `agents`) materialize their paginated iterator through it, so "what does sampling mean" has one answer and `itertools.islice` appears once. `_sampled` is orthogonal to caching -- those two accessors keep their own caching and (for `agents`) error policy, and only the list-materialization step is shared. The per-id accessors and their `prefetch_*` twins now share one `_fetch_site_*` method, so each per-site GET is spelled once: the accessor reads it lazily via `_cached_by`, the prefetch warms the same cache concurrently via `_prefetch_per_site` with the same callable -- the old duplicated GET (a local `_fetch` closure re-spelling the accessor's GET) is gone. See [[Per-rule prefetch]].
_Avoid_: routing an error-policy or sampling accessor through `_cached`/`_cached_by` (it would bury the per-accessor `try`/`except` or the `islice` the accessor exists to apply); "cache wrapper"/"memoize helper" (the noun is "cached accessor"); calling `_cached_by` a duplicate of `_cached` (single-value vs per-id are two distinct cache shapes, not one wrapped twice).

**SitePairing** (and the accessor `EnvSnapshot.sites_by_engine()`):
The single answer to "which sites pair to which scan-engine target." A frozen `SitePairing(by_engine: dict[int, list[int]], orphan_site_ids: list[int])`, returned by the cached accessor `snapshot.sites_by_engine()`. It owns the **base pairing invariant**: a site's `scanEngine` value is its pairing target (an engine id **or** a pool id), and a site is paired iff that value is *truthy* -- `0` / `""` / `None` / missing all mean orphan (engine ids are positive ints in v3; a `0` is not a valid engine, so treating it as orphan is the more correct reading, not a regression). It deliberately does **not** resolve pooling: it does not say which target ids are pools, expand pool membership, or compute unpaired engines -- that resolution lives in the topology builder ([[Report diagram]]), the only caller that needs it. The accessor concentrates the invariant that was re-derived in `single_engine_overload`, `local_engine_production_scope`, and `diagrams.build_topology`; those callers now read `.by_engine` (and topology reads `.orphan_site_ids` too) instead of each looping `snapshot.sites()` and re-deciding the guard. The operational `EngineUnpairedRule` already proved the shape -- it *receives* a pooled sites index rather than re-deriving it.
_Avoid_: putting pool resolution / unpaired-engine logic on `SitePairing` (it is the *base* grouping; pool semantics stay in the topology builder where they are needed -- widening it to a full pairing model gives most callers an interface they ignore); the `is not None` guard (the canonical rule is *truthy*, unifying the two rules' pool-blind guard with topology's); re-deriving `sites_by_engine` in any caller (the accessor is the one seam); "pairing map"/"engine index" as the noun (the noun is `SitePairing`).

**UserSnapshot**:
The narrow lazy-loading data container the User & Permission audit reads through -- peer to `EnvSnapshot` and `CloudSnapshot`, the third adapter at the `AuditCategory.build_snapshot` seam. It holds only the user/RBAC slice: `users()`, `authentication_sources()`, `user_2fa_enabled(uid)` (tri-state `bool | None` -- `None` = the `/2FA` endpoint 404'd and the rule must skip, not flag), `user_sites(uid)`, `user_asset_groups(uid)`, and the `is_users_endpoints_unavailable()` flag the category's `prime` reads to self-skip honestly on a `/api/3/users` 404. Constructed as `UserSnapshot(client)` -- it honours no sampling (the user accessors paginate the full population by design, so `full_scan` / `sample_size` never reach it) and needs no agents timeout, which is why it bypasses `build_env_snapshot`. Lives at `audit/user_permission/snapshot.py`, mirroring `CloudSnapshot`'s placement under its own category package. The seven User & Permission rules read it instead of the 38-accessor `EnvSnapshot`, so the slice each rule (and its test double `FakeUserSnapshot`) must learn is six members, not thirty-eight.
_Avoid_: "user data snapshot", "UserPermissionSnapshot" (the container holds no permission object -- the permission reasoning lives in the rules); "user cache".

**Per-rule prefetch** (the technique for an N+1 of per-site GETs):
The pattern a rule uses to collapse an N+1 of per-site GETs (`site_credentials`, `site_schedules`, `site_included_targets`) into one concurrent fan-out. The rule computes the exact slice of site ids it is about to iterate, then calls the matching `snapshot.prefetch_*(site_ids)` at the **top of its own `run()`** -- after which the per-site accessor inside the loop reads a warm cache instead of blocking on a sequential round-trip each. The seam is the **rule, not the `AuditRunner`**: the runner has no prefetch hook (its `prime` callable is an I/O early-exit, not a cache-warmer), and the prefetch is scoped to the one rule that needs it. The shared `_prefetch_per_site` helper fans out across `client.parallel_pages` workers, degrades to a sequential loop when that is 1 (or for a test double), and is **idempotent** -- already-cached sites are skipped, so when several rules in one category prefetch overlapping slices the first warms the overlap and the rest reuse it. A `Rapid7ClientError` on one site is swallowed and that site stays uncached, so the later sequential accessor retries it and surfaces the error in context -- the prefetch is a pure warm-up that never changes a rule's result or error semantics. Sampling is respected automatically: a fast-mode rule prefetches only its sampled slice. Distinct from a [[Server-side membership query]]: that one **eliminates** the per-asset loop (the question is expressible over `assets/search` fields, answer from `page.totalResources`); per-rule prefetch **keeps** the per-site loop but parallelizes its I/O -- the right tool when the cost is per-*credential*/per-*schedule* GETs that have no server-side aggregation. Used by `overlapping_scan_windows` (schedules + included-targets) and the four credential rules (`database_targets_no_db_credentials`, `web_spider_credentials_missing`, `site_credential_centralization_candidates`, `duplicate_credential_clusters`).
_Avoid_: "batch fetch", "warm the cache" as the canonical noun (the noun is "per-rule prefetch"); putting the prefetch in the `AuditRunner` or in `AuditCategory.prime` (the seam is the rule); calling it a server-side rewrite (it parallelizes the loop, it does not remove it).

## Operational-check orchestration

The operational checks (Scan Engines, Scan Activity, Asset Coverage, Data Quality) emit `RuleResult`s just like the audit categories, but their rules do **not** share a uniform contract: each rule takes its own positional args, checks share an upstream fetch through a closure (e.g. the single `/api/3/scan_engines` GET behind four rule cards), and gating is by *threshold* (`flag_missing_os`) not by a `rules:` registry. So they cannot reuse `AuditRunner` verbatim -- the shared spine is narrower.

**OpCheckRunner**:
The single deep module that owns everything identical across the four operational checks -- the envelope each `Check.run` repeats verbatim: the start-timer, the status rollup (`rollup_check_status`), the flattened-findings mirror (`flatten_findings`), the `rules_*` summary (`rule_summary`), and assembling the final `CheckResult`. It learns the per-check differences from an injected `OpCheckDescriptor`. The operational-vertical mirror of `AuditRunner`: one envelope, many checks -- the difference being its descriptor carries a single behavioural callable, not the audit registry/gate/snapshot trio.
_Avoid_: "op runner", "check engine", "op loop", "base check".

**OpCheckDescriptor**:
The descriptor value object injected into the `OpCheckRunner` that carries the only things differing between the four checks: identity (`name`/`description`) and one callable -- `produce_rule_results(client, config, snapshot) -> list[RuleResult]`. All the per-check irreducible behaviour (the shared-fetch closures, the peek→oversize→paginate dance in Data Quality, the heterogeneous per-rule `run(...)` calls, the `safe_run_rule` per-rule trap) lives inside `produce_rule_results`; the runner owns only the envelope around it. It is the adapter at the runner's seam. The mirror of `AuditCategory`, but thinner -- one callable where the audit descriptor needs three plus a registry.
_Avoid_: "op category", "op spec", "op profile", "op config", "audit category" (it is **not** a category -- categories are the four audit verticals; an operational check is not a vertical).

**The four operational check classes** (`ScanEnginesCheck`, `ScanActivityCheck`, `AssetCoverageCheck`, `DataQualityCheck`):
The thin `Check` adapters `__main__` registers. Each supplies an `OpCheckDescriptor` (its identity plus a `produce_rule_results`) and delegates to the `OpCheckRunner`; they hold no envelope logic. Mirror of the four audit check classes.
_Avoid_: "op orchestrator" for these -- the orchestrator is the `OpCheckRunner`; these are suppliers.

## Report rendering

**RenderState** (and its builder `build_render_state`):
The frozen bundle of the four *derived* values a render needs -- the trimmed state blob's serialized JSON, its content hash, the cross-run delta, and the metric rollup -- computed once by `build_render_state(*, results, tool_version, generated_at, base_url_host, prior_state) -> RenderState`. That builder is the single owner of the `project -> serialize -> compute -> metrics` sequence: `state_engine.project` builds the blob (None if oversized), serialization + the SHA-256 content hash follow only when the blob exists, the delta is computed only with both a blob and a `prior_state`, and metrics are always computed. It is pure -- no I/O, no HTML -- so the pipeline is testable without rendering (see `test_build_render_state_*`). `render_report` calls it once and passes the `RenderState` fields straight into `template.render`. Before this, those four values were *mutated onto* `ReportContext` inside `render_report` in a fixed-but-implicit order; now `ReportContext` is `frozen=True` and **inputs-only** (title, generated_at, host, version, config_path, results, thresholds_table, inventory_totals) -- the inputs/outputs entanglement is gone and no caller reads a computed field back off the context (none ever did -- they were write-only intermediate state). Respects ADR-0002: this reorganizes the *live* render orchestration only; the `findings_of` / `compute.index` twin is untouched.
_Avoid_: "render context" for the computed bundle (the context is the *inputs*; the bundle is the `RenderState`); re-adding `delta`/`metrics`/`state_blob_json`/`content_hash` to `ReportContext` (they are derived, not given -- they belong on `RenderState`); calling `build_render_state` a wrapper (delete it and the project/serialize/compute/metrics order reappears inline in `render_report` with no single place to test it).

**RuleCardView** (and its builder `build_card_views`):
The frozen per-rule-card view-model that pulls the three *decisions* the report template used to make inline back into pure Python -- `RuleCardView(rule_id, search_text, severity_css, changed)`, one per rule card, built by `build_card_views(results, *, delta) -> dict[str, RuleCardView]` keyed by `rule_id` (unique per run -- it is the delta signature index key). The template looks up `card_views[rr.rule_id]` and emits its fields; it no longer *computes* them. The three fields each retire a cross-language decision: `search_text` was the `data-search-text` Jinja string-slice the search JS did `indexOf` against (the format contract lived in two languages with nothing enforcing it); `severity_css` was the `{{ 'fail' if … else 'warn' if … else 'pass' }}` clamp spelled twice; `changed` was the **JS state-blob re-walk** (template lines ~1024-1033) that re-collected `delta` signatures and re-matched them against `state.results -> rule_results -> findings` -- a fourth spelling of the signature walk after `findings_of` (live), `project`'s loop, and `compute.index` (dict). `build_card_views` resolves the changed set in Python straight from `delta` (every delta finding already carries `rule_id`, attached by `compute.index`), so the JS drops to a chip toggle and the walk twin is gone. Pure -- no I/O, no HTML -- so each card decision is unit-testable (see `test_build_card_views_*`); it is the test surface the template never was. Respects ADR-0002: it reads the *live* delta dict the render already holds, it does not add a walk over the serialized blob.
_Avoid_: "card model"/"card context" (the noun is `RuleCardView`); re-deciding `search_text`/`severity_css`/`changed` in the template once the view carries them (that re-splits the contract the view exists to unify); re-introducing the JS state-blob walk to mark changed cards (the `changed` boolean is computed once, server-side, from `delta`); calling `build_card_views` a fourth signature-walk twin (it consumes `delta`'s already-walked output -- it does not re-walk findings).

**findings_of**:
The single iterator over a **live** `CheckResult`'s findings -- `findings_of(check) -> Iterator[(rule_id, Finding)]`. It owns the one fragile invariant the render path kept hand-copying: walk `rule_results`' findings **xor** the top-level `findings` mirror, never both (indexing both double-counts a finding in the delta-blob signature index). When a check has `rule_results`, it yields each rule's findings tagged with that rule's `rule_id`; for a legacy (pre-0.2.6) check with only top-level findings, it yields them tagged with the check `name`. The canonical statement of the xor decision over live objects -- the render path (`_annotate_findings`) and the metric rollup (`report._metrics`) both consume it; do not re-inline the xor branch at a live call site.

There is **one deliberate twin**, not a copy: `state_engine.compute`'s `index()` re-encodes the same xor over the *deserialized* state blob (plain dicts read back from a prior report, possibly written by an older tool version). It cannot call `findings_of` (different input type) and must stay tolerant of stale blobs, so the two walks are a genuine fork across the serialize/deserialize seam -- kept separate on purpose. See [docs/adr/0002-state-blob-walk-stays-separate-from-findings-of.md].
_Avoid_: "finding walker", "iterate findings" (the noun is `findings_of`); calling the dict-side `index()` a duplication to be collapsed -- it is the dict twin, recorded in ADR-0002.

**Section rail**:
The persistent left-column navigation listing the report's checks -- one entry per `section.check`, each carrying a status dot, the check name, and a count of fail/warn findings, so the rail reads as an at-a-glance triage map. It scroll-spies the currently-viewed section (active entry highlighted) and reflects the active severity filter (entries with no visible cards dim; count badges show *visible* matches, not totals). It does **not** hide content-area sections -- the filter's card-hiding CSS is untouched.
_Avoid_: "sidebar", "TOC", "table of contents", "nav menu" (the noun is "section rail"; "sidebar" is the layout slot, "section rail" is what lives in it).

**Content column**:
The right grid column that holds everything the report already rendered -- hero, inventory, delta, metric grid, summary table, and the check sections -- capped at its historical reading width. The `max-width` that used to live on `<body>` lives here now; the page is a grid shell of `[section rail | content column]` that collapses to a single column (rail → a native `<details>` "Jump to section" disclosure) below the narrow breakpoint and in print.
_Avoid_: "main", "content area", "right pane" (the noun is "content column"; it is one half of the grid shell).

**View switch** (and the **Findings view** / **Diagrams view**):
The top-level control that selects which of the report's two views is shown, splitting the body **below the shared hero** (the hero -- title + verdict -- stays visible in both, as the masthead). The **Findings view** is the textual triage view: inventory, metric grid, summary table, the [[Section rail]], the filter bar, and the check sections with their rule cards. The **Diagrams view** holds the three [[Report diagram]]s (health status map, coverage bands, scan topology) and nothing else. The switch is **CSS-only** -- hidden `<input type="radio" name="view">` plus `<label>` tabs, the `:checked` panel shown via a sibling combinator -- so it works with **JavaScript disabled** (matching the report's no-JS contract) and uses **no `location.hash`** (deliberately, so it cannot collide with the filter bar's hash sync or the scroll-spy/jump logic, which own the hash). The default-checked radio is the Findings view, so the diagrams take no vertical space until asked for. The filter bar belongs to the Findings view and is hidden when the Diagrams view is active (diagrams aren't filterable). `@media print` overrides the switch so **both** views render -- a printed/PDF report is a complete archival artifact, not a snapshot of the active view; the view-switch labels hide in print like the filter bar does.
_Avoid_: "tab"/"report tabs" (it is a CSS-radio control, not a tab widget -- the noun is "view switch", the panels are "Findings view"/"Diagrams view"); "panel" as the canonical noun (say "view"); a `:target`/anchor-based switch or any use of `location.hash` for view state (the hash is owned by the filter sync + scroll-spy; a `:target` switch would clobber and be clobbered); a JS-driven switch (it must work with JS off); moving the hero inside a view (it is the shared masthead -- the verdict shows in both views).

**Report diagram** (and its builder module `diagrams.py`):
An inline `<svg>` figure rendered in the report's [[View switch|Diagrams view]] (all three figures live there together, not inline in the check sections), built in pure Python by `diagrams.py` from numbers the run **already holds** -- it issues **no API calls** and reads no live client. Two data seams feed it: the coverage figure reads `CheckResult` rule-summaries + `InventoryTotals`; the topology figure reads a `TopologyData` view-model. Both view-models are built in the **report layer** by `report.build_inventory_totals(snapshot)` / `report.build_topology(snapshot)` (which read **already-cached** snapshot accessors -- `sites`, `scan_engines`, `scan_engine_pools`, `sites_by_engine`, the inline `site_asset_count` -- and each return `None` on any accessor failure so the figure is skipped); `__main__` only wires them onto `ReportContext`. Either way `diagrams.py` never touches a client or snapshot at render time. Each figure has an `extract_*`/`build_*` (coverage) or `build_topology`/`build_topology_svg` (topology) split -- a data half and a pure layout half -- mirroring the `build_render_state` / `build_card_views` pure-builder-feeding-the-template pattern; both halves are unit-testable without rendering. The SVG is themed with the **report's own** CSS variables (`--fail-bg`, `--pass-fg`, `--border`, ...) through purpose-built `dg-*` classes -- there is one theme system and one toggle. The archify **cardinal rule** -- a styled box's (possibly semi-transparent) fill must sit on an opaque `dg-mask` rect of identical geometry, or arrows/segments bleed through -- lives in one helper, `_masked_rect(parts, x, y, w, h, cls, *, rx=6)`, which appends the mask-then-styled pair; the seven box sites across the three builders call it (the per-figure label/count/sub placement legitimately varies and stays in each builder). `test_diagrams_mask_invariant` locks "every styled box is masked" so a future builder can't silently drop the mask. The [archify skill] is the **design spec** (semantic fills, two-rect mask, arrow markers, typography scale), not a runtime dependency: no Node, no archify JS, no export toolbar, no second `[data-theme]` toggle (see [docs/adr/0008-report-diagrams-port-archify-design-not-runtime.md]). A diagram whose inputs are missing or untrustworthy returns `None` and the figure is omitted (the Diagrams view, and its view-switch tab, render only when there is at least one diagram) -- a diagram that can't be honest does not render (the same "lines we can't stand behind" discipline as the ghost-asset rule). `report.build_section_diagrams` assembles the `{check_name: svg}` map; the template iterates it into the Diagrams view, each figure captioned by its check name (the status map is its own `status_map_svg`, rendered first). The check-name constants (`_COVERAGE_CHECK_NAME`, `_SCAN_ENGINES_CHECK_NAME`) live in `report.py`, and `diagrams.extract_coverage_counts` takes the coverage check name as a `check_name=` argument rather than hardcoding it -- so `diagrams.py` doesn't decide which check it reads, the report does. (The map is still keyed by check name, now used as the figure caption rather than to place the figure inside a section.)

The **coverage bands** figure: honest *nested* threshold bands (all assets ⊇ stale `>Nd` ⊇ never-scanned `>Md`), never a funnel implying a partition, because never-scanned is a subset of stale and agent-only/ghost are cross-cutting flags.

The **scan topology** figure: *engine-centric* columnar lanes (Sites → Engines/Pools). Sites are aggregated (a paired-sites bucket + an orphan bucket), never drawn individually, so the node count is bounded by engines+pools regardless of console size -- the fixed lanes make layout collision-free by construction (no free-graph reflow). Pairing semantics match the engine rules: a site's `scanEngine` is its pairing (an engine **or** a pool id); an engine with no direct sites that is in no pool is *unpaired*; an engine's load is the sum of its directly-paired sites' asset counts; overloaded mirrors `single_engine_overload` (≥2 sites over threshold).

The **health status map** figure: one stacked bar per check (those with `rule_results`), segments proportional to that check's per-rule status counts, drawn in pass→warn→fail→error→skipped order with a legend. Reads only the already-computed per-rule statuses (no snapshot, no API) via `extract_status_map(results)`. Unlike the per-check figures it spans all checks and renders in the **Summary** section, so it is its own template variable (`status_map_svg`, built by `report.build_status_map`) -- not part of the `section_diagrams` map. `error` and `skipped` get their own (info / muted) segment colors, never folded into `pass`: error = couldn't evaluate, skipped = disabled, neither is a health signal.
_Avoid_: "chart"/"figure" as the noun (it is a "report diagram", built by `diagrams.py`); calling archify a dependency (it is the design spec -- the runtime ports its taxonomy, not its code); a coverage *funnel* or any stacked bar that sums overlapping populations to a whole (the bands are nested, not disjoint); drawing **individual site boxes** in the topology (it is engine-centric and aggregated -- per-site boxes don't scale and reintroduce the free-graph layout problem); folding `error`/`skipped` into `pass` in the status map (they are non-health states with their own colors); putting the status map in `section_diagrams` (it spans all checks and is its own `status_map_svg`, rendered first in the Diagrams view); a second theme toggle or archify's `c-*`/`a-*` namespace (diagrams reuse the report's vars via `dg-*`); building `TopologyData` inside a rule or letting `diagrams.py` read the snapshot (the view-model builders live in the **report layer** -- `report.build_topology` / `build_inventory_totals` -- so the render path stays API-free and `__main__` only wires); putting the view-model builders back in `__main__` (it wires only -- view-model construction is a report concern); having a check emit report-shaped output (the `rule_id`/summary-key knowledge lives only in `diagrams.py`, the figure→section binding only in `report.build_section_diagrams`).

## Check dispatch

**Check** (the protocol):
The uniform interface every check (operational and audit) presents to `__main__`: `run(client, config, *, snapshot=None, cloud_client=None, progress=None) -> CheckResult`. All eight checks accept the same optional-kwarg superset and use only what they need -- op-checks read `snapshot`, cloud-drift reads `cloud_client`, audits read `progress`. The signature is honest: it matches how `__main__` actually calls every check, so dispatch is a single uniform loop with no per-check special-casing. A check that ignores a kwarg simply doesn't reference it.
_Avoid_: a per-check `run` signature that omits kwargs other checks need -- `__main__` must never branch on check identity to decide which kwargs to pass. The thing that varies between checks is *what they read*, never *what they're handed*.

**_REGISTRY**:
The ordered `dict[str, type[Check]]` in `__main__` mapping each check's config-toggle name (`scan_engines`, `configuration_audit`, …) to its `Check` class. Dispatch order and the `checks:` enable toggles key off it. Adding a check is one `_REGISTRY` entry plus the check class -- no dispatch-branch edit, because every check is called identically. `__main__` still **owns** the registry literal, but **injects** it into the `CheckDispatcher` (it is no longer read as a module global from inside the dispatch loop -- the seam is now explicit).
_Avoid_: "check map", "check table".

**CheckDispatcher**:
The single module that owns the **whole-run** dispatch loop -- the *inter*-check envelope `__main__` used to carry inline in `_run_checks`: the per-check `checks.get(name)` enable-gate (and the synthesized `status="skipped"` `CheckResult` for a disabled check), the `progress` start/finish choreography with its `idx/total` numbering, per-check `time.monotonic()` timing, and the per-check exception trap that turns an escaped error into a `status="error"` `CheckResult` instead of aborting the run. `CheckDispatcher(registry).run(client, config, snapshot, *, cloud_client=None, progress=None) -> list[CheckResult]` takes the registry as a **constructor arg** (was a module global the tests had to monkeypatch -- the seam is now a parameter, so a test passes a fake registry directly). It is deliberately **not** a fourth peer of `AuditRunner` / `OpCheckRunner`: those each run *one* check and own the *intra*-check envelope (timer → rollup → assemble a single `CheckResult`); `CheckDispatcher` sits one level **above** them, looping the registry and dispatching each `Check.run` -- a check that is itself an audit category runs its own `AuditRunner` inside that call. Lives at `checks/dispatcher.py`. `__main__` shrinks to wiring: build client/snapshot/progress, `CheckDispatcher(_REGISTRY).run(...)`, render.
_Avoid_: "CheckRunner" / treating it as a peer of `AuditRunner`/`OpCheckRunner` (those are single-check intra-envelope runners; this is the loop above them -- the name must say *dispatch*, not *run one check*); "check loop"/"dispatch helper" as the noun (the noun is "CheckDispatcher"); reading `_REGISTRY` as a global inside the loop again (it is injected so the dispatch seam is testable without monkeypatching).

## Rule registration

**load_rules**:
The side-effect importer that turns a `rules/` package into a populated registry -- `load_rules(package)` walks the package with `pkgutil.iter_modules` (sorted, for deterministic order) and imports each module so its `@register*` decorator fires. It replaces the hand-maintained "import every rule module" lists each audit category's `__init__` used to carry (a third, silent-on-omission place to register a rule). The directory is now the single source of truth: drop a decorated rule file in `rules/`, it registers. Module order is alphabetical and stable; only the cosmetic footer run-hash depends on it (the cross-run delta is signature-keyed in `state_engine.compute`, so ordering never affects delta correctness -- see [findings_of]).
_Avoid_: "discover_rules" (implies a return value; this registers via side effect and returns None), "register_all", "rule scanner". The registration act is still `@register*` on each rule; `load_rules` only ensures the modules get imported.

## Configuration loading

**Field floor** (the int lower-bound carried on the dataclass field):
The minimum an int config field may take, declared once on the field itself via `field(metadata={"min": N})` and enforced by `_from_dict`'s existing per-field loop -- `min=1` for a positive-only field, `min=0` for a non-negative one. It replaces the `POS_*`/`NN_*` field-name tuples and the four threshold `post_validate` lambdas that used to re-declare, in string form, which int fields were positive: the constraint now lives where the field is declared, so there is no separate list to keep in spelling-sync and a mistyped field name is impossible (there is no name to type). `_from_dict` maps the bound back to the frozen error string at raise time -- `min == 1 → "must be a positive integer"`, `min == 0 → "must be a non-negative integer"` -- so the wording is byte-identical to what `_check_scalar` / `_positive_int_fields` emitted before, and the existing config tests are the regression net (the 1.0 frozen contract holds without test edits). The pure lower-bound checks across **all** scalar blocks migrate to a field floor (thresholds, `rapid7` timeouts, `cloud_integration` timeouts, the audit-body `sample_size`/`agents_timeout_seconds`); `_build_thresholds` collapses to four plain `_from_dict` calls.
_Avoid_: "min validator"/"field constraint" as the noun (the noun is "field floor"); re-introducing a per-block list of which fields are positive (the floor *is* that fact, stated on the field); pushing a `max` bound into `_from_dict` to absorb the `rapid7` ranges -- see [[Validation hook]] for why ranges stay hooks.

**Validation hook** (`post_validate`, the home for everything that is *not* a field floor):
The per-block callable `_from_dict` runs after construction, holding the irreducible validation that a [[Field floor]] cannot express: a *range* (`rapid7.parallel_pages` `[1, 16]`, `rapid7.page_size` `[1, 500]` -- a floor plus a ceiling, and the `parallel_pages > 8` *warning*, which is policy, not a bound), and a *nullable-with-custom-wording* field (`report.delta_max_age_days` accepts `>= 0` **or** null and raises its own `"expected non-negative int or null"` string). The seam division is the point: **a field floor owns "what is the minimum for this int"; a validation hook owns "everything that isn't a floor"** -- ranges, warnings, nullable+bespoke-message. Each side has a distinct job, so neither leaks the other's shape. `_positive_int_fields` survives only because the two `rapid7` range hooks still do a lower-bound check alongside their ceiling; it is not dead, but it is no longer the threshold mechanism.
_Avoid_: folding ranges or the `parallel_pages>8` warning into a `min`/`max` metadata pair on the field (it would drag a second error-string shape -- `"must be in range [lo, hi]"` -- into `_from_dict`'s one loop, re-creating the `post_validate` problem under a new name and making the mechanism shallower, not deeper); calling `post_validate` a leftover to be eliminated (it is the deliberate other half of the seam).

**ConfigBlockSpec**:
The descriptor value object that carries the only things differing between the four rule-bearing audit config blocks (`audit`, `user_audit`, `cloud_drift`, `template_audit`) when `config.py` parses them: the dotted `path` that prefixes every `*.rules` error message (`"audit.rules: …"`), the `body_path` that prefixes body-level messages, a lazy `registry` accessor (a zero-arg callable that imports and returns *this* category's valid rule ids -- the lazy import lives inside it to dodge the config↔audit circular import, the rationale that used to sit on `_registry_rule_ids`), and an optional `body: BodySpec | None`. It is the adapter at the config builder's seam -- pure data plus the two callables (`registry`, and `body.pv` when bodied). The config-parse mirror of `AuditCategory`: one builder, four blocks.
_Avoid_: "AuditCategorySpec"/"AuditConfigSpec" (the first collides with `AuditCategory`, the *runtime* descriptor injected into `AuditRunner`; the second sits one rename from the concrete `AuditConfig` dataclass it parses -- both invite the exact term-drift this glossary prevents); "config dialect" ("dialect" is reserved for `ApiDialect`, the v3/v4 API-shape difference).

**BodySpec**:
The inner descriptor `ConfigBlockSpec.body` points at when a block has a scalar body beyond its `rules:` mapping -- `audit`/`user_audit`/`template_audit` each have one; `cloud_drift` is `body=None` (rules-only). It carries the config dataclass `cls`, the `pv` post-validate hook (the `sample_size` / `+agents_timeout` positive-int checks), and `required: frozenset[str]` -- the explicitly-required keys. `required` defaults to `frozenset()` because `audit`/`user_audit`'s fields have no defaults, so `_from_dict`'s MISSING-derivation already requires them; only `template_audit` populates it (`{enabled, full_scan, sample_size}`), whose dataclass *gives* those three defaults, so without the explicit set an empty `template_audit: {}` block would silently validate instead of erroring. The `body is None` arm of the builder runs the rules-only path (`_validate_dict_schema` + `_validate_rules_block`); the bodied arm runs the required-key gate, `_from_dict`, then `_validate_rules_block`.
_Avoid_: "the audit body" used loosely for the whole block (the block is the `ConfigBlockSpec`; the body is only its non-rules scalar slice); folding `required` away by trusting `_from_dict`'s derivation (it is load-bearing for `template_audit` precisely because that config's fields carry defaults).

**_build_rule_audit_config**:
The single deep builder that owns everything identical across the four rule-bearing config blocks -- the `data is None → default` short-circuit, the `dict(data)` / `pop("rules")` / `isinstance` mapping checks, the required-key gate, the `_from_dict` body parse, and the `_validate_rules_block` + `replace` rule-merge. It learns the per-block differences from an injected `ConfigBlockSpec`. It absorbs the four near-identical `_build_*_audit_config` bodies and the `_registry_rule_ids()` 4-tuple every one of them used to unpack-and-discard-three-of. Error wording is byte-identical to the pre-collapse builders by construction (the `path`/`body_path` carry it), so the existing config tests are the regression net -- the 1.0 frozen contract on error strings holds without test edits.
_Avoid_: "the config factory", "make_audit_config"; calling it a wrapper (delete it and the pop/isinstance/`_from_dict`/required-gate/merge body reappears at four call sites -- it concentrates that complexity, it does not pass it through).

**The four config builders** (`_build_audit_config`, `_build_user_audit_config`, `_build_cloud_drift_config`, `_build_template_audit_config`):
The thin adapters that survive the collapse as one-line shims -- each holds its category's `ConfigBlockSpec` literal (and default) and delegates to `_build_rule_audit_config`. They keep their names because they are private and called only by `_build_app_config` and ~56 test call sites; preserving the names keeps those tests untouched, so the suite stays an *independent* witness that behaviour is unchanged rather than a co-edited party to the refactor. Analogous to `Rapid7Client`/`CloudClient` wiring an `ApiDialect` into an `HttpTransport`: the depth lives in the shared builder, the per-category names are the seam callers (here, tests) hold onto.
_Avoid_: "duplicate builders" (post-collapse they are one line each, no logic to duplicate); deleting them to call `_build_rule_audit_config` directly at the 56 test sites (that edits the regression net, forfeiting its independence).

## Rule result-build

**AuditRule**:
The base class the concrete audit rules across all four categories inherit, sitting between the `Rule` *protocol* (the structural interface every rule satisfies) and the rule classes. It owns one method -- `result(findings, *, severity, summary=None, examined=None, failed=None, sampled=False, sample_info=None, card_summary=None) -> RuleResult` -- which reads the rule's own identity (`rule_id`, `rule_name`, `description`, `sources`, `default_severity`) off the subclass and delegates to `make_rule_result`, the same builder the operational checks already use. Before `AuditRule`, every `return RuleResult(...)` site in every rule hand-rolled the `fail > warn > pass` status derivation, the `card_summary` `{examined, passed, failed}` shape, and the `sources=list(...)` coercion -- the op vertical's `make_rule_result` had absorbed exactly this build, but the audit rules never adopted it. `AuditRule.result` closes that gap so both verticals share one result-build. The config-overridden run-time `severity` is passed **explicitly** at each call site (not read from `self.default_severity`), because the two differ when an operator overrides a rule's severity and the `RuleResult.severity` field feeds the state blob -- so the base stays stateless (no run-call-order coupling) and the value's provenance stays visible. `AuditRule` *structurally* satisfies the `Rule` protocol, so the registry and `AuditRunner` dispatch are untouched by inheritance; `@register` still keys on each rule's `rule_id`.
_Avoid_: "BaseRule"/"RuleBase" (the term mirrors `AuditRunner`/`AuditCategory`, audit-side only -- op-checks call `make_rule_result` directly, they are not rule classes); "RuleResult factory"; calling `result()` a wrapper (it is the single owner of the audit-side build, not a pass-through -- delete it and the `fail > warn > pass` block reappears at ~50 call sites).

## Severity rollup

**worst_status**:
The single owner of the status precedence `fail/error > warn > pass`. `worst_status(items) -> Status` reduces any iterable of status-carrying items -- anything with a `.status` field, which is both `RuleResult` and `CheckResult` -- to the worst status: `fail` if any item is `fail` or `error`, else `warn` if any is `warn`, else `pass`. It lives in `audit/rule_rollup.py` beside the other reductions. Three call sites that each used to hand-write this precedence now read it from here: the two runners' check-level rollup (via the `rollup_status` alias), the report hero verdict (`report._verdict`), and the process exit code (`__main__.pick_exit_code`). The latter two reduce the run's `CheckResult`s with `worst_status`, then map the single returned `Status` through a plain status→presentation table -- `_verdict` to a `(css-class, label)` tuple, `pick_exit_code` to the `EXIT_*` int -- so neither re-encodes the ordering. `skipped` is not a problem state: it is neither `fail`/`error` nor `warn`, so it falls through to `pass` in the reduction (a category or rule that self-skipped never escalates the run), matching the prior behaviour of all three sites.
_Avoid_: "severity precedence" written inline at a call site (the ordering lives once, in `worst_status`); "max severity"/"highest severity" (the result is a `Status`, and `error` is not on the `Severity` scale -- the reduction is over statuses, not severities).

**rollup_status**:
The check-level application of `worst_status`: turning a check's `list[RuleResult]` into the check's `CheckResult.status`. It is a bare alias -- `rollup_status = worst_status` -- not a second body, because the reduction is identical (a check is `fail` if any rule failed/errored, `warn` if any warned, else `pass`). Kept as a named entry point so the two runners and the `rollup_check_status` op-side alias import a domain-named function rather than the general `worst_status`; `rollup_check_status` continues to alias `rollup_status`, one level further. The chain is `worst_status` (the body) ← `rollup_status` (alias) ← `rollup_check_status` (alias).
_Avoid_: making `rollup_status` a delegating `def` (`return worst_status(x)`) -- a bare alias is the truthful expression of "same function, second name"; a wrapper adds a frame and a second signature to keep in sync for nothing.

## Temporal parsing

**timewindow** (`audit/timewindow.py`):
The single deep module owning the InsightVM time-shape parsing both verticals kept re-spelling -- three functions behind a tiny interface: `parse_iso(value) -> datetime | None`, `parse_duration(value) -> timedelta`, and `windows_intersect(a_start, a_end, b_start, b_end) -> bool`. It lives beside `rule_rollup.py` (the precedent for a shared reduction primitive both verticals import) because the dependency direction `checks -> audit` is already the convention -- op-checks import `RuleResult`, `EnvSnapshot`, and the rollup helpers from `audit/`, so a temporal helper there is consumed, not a layer inversion. Before `timewindow`, `_parse_iso` was copied across **six** files (`overlapping_scan_windows`, `scan_report_schedule_overlap`, `engine_version_drift`, `cloud_drift/scan_engine_cloud_registration`, `checks/scan_activity`, `checks/scan_engines`), `parse_duration` + the `PT[nH][nM][nS]` `_DURATION_RE` + `windows_intersect` across **two**. The copies had quietly **diverged**: five returned a naive-or-aware datetime as the API happened to emit it, while only the cloud-drift copy normalized a naive parse to aware UTC -- and that divergence was a latent `TypeError` waiting in `scan_engines` (`now - last_refreshed`, `now` aware) and `engine_version_drift` (`refreshed_at < stale_cutoff`, both aware), which crash whenever the Console returns an offset-less timestamp. `timewindow.parse_iso` adopts the cloud-drift author's already-correct **always-aware-UTC** behaviour as the one contract (naive parse -> `tzinfo=utc`, `isinstance` guard folded in), so the extraction *is* the bug fix: the knowledge trapped in one copy now covers all six.
_Avoid_: "isotime"/"temporal"/"date utils" (the noun is "timewindow" -- the dominant caller asks scan-window questions, and `windows_intersect` is interval math, not ISO parsing); folding `_applicability.parse_iso8601_seconds_to_ms` into this module (it is a **different grammar** -- fractional `PnS`/`PTnS` -> `float` milliseconds for discovery timeouts, not `PT[nH][nM][nS]` -> `timedelta` -- and merging it would drag two return types and two regexes behind one interface, making the module shallower; it stays at the rule layer in `_applicability.py`); re-introducing a per-caller `_parse_iso` "to preserve the old naive behaviour" (the naive behaviour was the bug).
